# How-to：项目负责人怎样一步一步推进

> **当前使用入口（2026-10-29）：** [两阶段执行总表](../planning/vmware_soc_twin_task_execution_20261029.md)与[主看板](../../.agents/kanban/KANBAN.md)为当前接续入口。第一阶段在VMware运行真实服务/管理/IPC/浏览器界面，第二阶段迁移并实板实屏验收。旧文中的MS/CLI启动与历史模拟记录仅保留其原范围；新服务尚未交付，不存在可照抄运行的完整孪生启动命令。

**现在先提供已有工程位置，团队核查后再开发。** 本手册与 [[AI_SoC_协作方案/13_简化版_从电脑模拟到真机]] 是同一执行方案的详细/简要阅读视图；任务和依赖统一引用 [[AI_SoC_协作方案/03_实施步骤与首个闭环]]，不另建第二套。

## 你主要做什么

你是 HUMAN 项目负责人，决定产品先做什么，协调真实资料和人员，查看交付结果。先明确指定主对话承担 COORD，再由实际执行者承担模块、QA、INTEGRATOR 等岗位。岗位不是固定 Agent；同一任务的作者与独立检查者分开。定义统一见 [[AI_SoC_协作方案/02_模块与Agent职责]]。

| 顺序 | 你的动作 | 团队的动作 | 你应看到的结果 |
| --- | --- | --- | --- |
| 1：交接已有工程 | 给 Linux 环境、源码目录、访问方式和已有编译/启动命令；未知写待提供 | MS-01 登记现有成果，MS-02 独立复现；不换到另一种示例配置 | 路径、版本、配置、可重复运行记录；用户报告与团队复现分开 |
| 2：确认最小通信 | 回答真正影响首轮目标的问题，不需要自己写协议字段 | MS-03 调查，MCQ 在必要时补固件接口，MS-04～06 核对真实样例、约定和独立预期 | 发什么、回什么、何时成功/失败说得清楚 |
| 3：接入 SoC 主控查询 | 查看版本和温度查询演示及失败记录 | MS-18 先交主机工程；MS-07～10 实现，MS-20 交候选，MS-11 独立验收 | SoC→MC 通过，范围写 MC-only；暂不要求 UI、从控或三总线 |
| 4：加入从控 | 提供自定义 SCM 源码及主从协议线索 | MS-12/13 调查，MS-19 交独立预期；主控通过后 MS-14～16 实现，MS-21/17 交候选并验收 | Ubuntu SoC 程序＋真实 MC/TH 查询结果；原始轨迹及故障范围清楚 |
| 5：增加产品功能 | 选择当前必需行为与暂缓项 | 将短作业、混色、文件、准入、UI、三总线等工作包继续拆小任务 | 每次一项明确行为、相应测试和准确版本 |
| 6：真实设备与交付 | 协调板卡、维护者和可用时段，确认产品交付范围 | BSP/MCU/QA 核对实际条件，逐部件替换并验证；Integrator 打包 | 模拟/实物证据分开，版本组合、恢复说明及已知限制齐全 |

## 第一轮你可以直接填写

```text
Linux 环境：
工程总目录：
MC Marlin 目录：
SCM 自定义 Marlin 目录：
SoC 工程/forward 入口：
VMware SSH 地址、USB 直通设备：
已有编译、启动命令：
这台开发机怎样访问：
```

版本和配置由团队核查。工程是否接入及复现以 MS-01/02 的实际证据为准；提供路径不等于已经独立运行成功。

## 怎么开始和继续

先指定唯一 COORD 并明确人工转交或本轮子 Agent 反馈，复制指令统一见 [[AI_SoC_协作方案/07_第一次启动与日常使用]]。

每张派单检查任务、输入版本、可改范围、完成标准和实际接收方；明确人工占用期限、检查点与续领回执，采用 [[AI_SoC_协作方案/templates/角色任务提示词]] 的回执；记录岗位与实际会话，不能只写“某工程师负责”。按当前 MS 任务派单，不把 TASK-001～018 工作包整张扔给 Agent，也不再次确认已经确定的 Marlin、真实台架和 VMware USB 直通方向。

首次查询先由 MS-03 复核当前固件，缺 USART1 RX/版本/温度应答时由 ENG-MC 按 MCQ 实现/验收，MS-04 再取实收样例；MS-05 区分 D20 原稿、固件实现和可消费约定，迁移取舍留待明确接受。

## 你怎样判断完成

找四样东西：**准确版本、可运行方法、预先约定的结果、实际检查记录**。界面显示成功或 Agent 说完成，都不足以单独通过。

- MS-02 通过表示准确 MC 固件构建/台架启动记录已独立复现，尚非查询通过。
- MS-11 通过表示 SoC→MC 查询范围已验收。
- MS-17 通过表示真实双 MCU 查询范围已验收，须说明接口/故障与固件版本范围。
- MS-22 检查实际团队交接；首阶段还要看 MS-11、17、22 三份对应结果。
- 真实打印和混色质量另看实物证据，不从模拟状态推断。

看板状态是 `Backlog → Ready → InProgress → Review → Verify → Done`；阻塞另记原因。建议主责不是认领人；实时状态只看当前卡，不在手册固定写某张卡未运行。

## 每天只问这几件事

```text
请读取当前任务和交接，告诉我：做成了什么、怎样证明、缺什么、下一步是什么。
需要我决定的给容易比较的选项，其他已授权工作按依赖继续。
没有执行的检查写未执行；所有报告标明 MC-only、MC+SCM 或实机范围。
```

采用主对话本轮委派方式时，COORD 收取子反馈并汇总成果和问题；采用独立对话时，由你将结果位置通知 COORD。没有已部署后台服务时，本轮结束后需要再次发消息继续。失败按 [[AI_SoC_协作方案/12_项目风险清单与失败预案]] 保留版本、日志和重现步骤，再交对应岗位处理。

## 后续还需要你协调什么

已设立的 ENG-MC/ENG-TH 实际人员/会话与本轮权限、主从业务资料、目标 SoC SDK/板号与设备资源、实际混色机构/材料样例、产品交付目标。这些按受影响任务解决，不将全部未知捆绑成首次主控查询的门槛。

需要生产 MCU 扩展或硬件改动时落实对应负责人；已有接口可满足的只读联调，不要求先改 MCU。主对话也不会自动联系资料中的人员或替你取得源码权限。

试点的简短验收原件见 [[AI_SoC_协作方案/pilot_requirements_20261008_083854]]；你需要选择的后续产品功能见 [[AI_SoC_协作方案/product_feature_catalog_baseline]]。
