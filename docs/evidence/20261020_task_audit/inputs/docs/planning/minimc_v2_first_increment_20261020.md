## 本次已执行的第一项核对

对[本地 Rev 2.0.3 原稿](../specs/README.md)执行只读算术核对，使用 Python 标准库 `binascii.crc_hqx(data, 0xFFFF)` 重新计算 §7 五个完整帧，并用逐位多项式算法检查 CRC 查表：

- 五个帧的 CRC、`L+14` 物理长度及版本位均匹配，5/5。
- CRC 表 256/256 项与多项式 `0x1021` 推导值相同。
- V04 的 CRC 虽正确，但其零字节载荷与 §5.1/§5.2 的急停 2 字节规定仍冲突；它只能作为帧校验样例，不能据此宣布急停业务合法。

准确原文 SHA256、算法、输入帧和计算值见[预核对证据](../evidence/20261020_protocol_preflight/protocol_preflight.json)。这是文档算术核对，没有生产编解码器实现或独立 QA 通过记录。

离线测试的黄金预期必须在实现前从原文和独立 CRC 算法取得，不能仅做同一个编解码器自编码/自解码后声称正确。作者可执行测试；独立检查仍由不同实际执行者留下结果，不能给自己换角色名签署。

## 后续顺序与各自前置

1. **MC/TH 构建复现**：独立核对 MS-01 登记，再落实 MS-02 的输出和执行范围，分别编译两端 App，保存日志、版本头、size 和制品哈希；当前仍没有 MCU 构建通过证据。
2. **AP 请求会话与串口层**：在 wire contract 和编解码检查完成后，实现端点配置、有界读写、一次一个待确认请求、响应匹配、超时/断链和 RTT 采集。请求级期限和重试策略先在任务中明确；不能从帧解析器的 50ms 自动推导。
3. **MC USART2 迁移与本机版本/PING 响应**：先归档 MCU 实施方案，按 `mcu-p3/AGENTS.md` 完成所要求审批，再分步处理旧屏 RX、解析、TX 的所有权，接入 v2.0；先验收 AP↔MC。不能在协议库票里顺手改固件。
4. **MC↔TH 路由与 TH 响应**：在主控链路通过和板间配置/协议范围明确后，MC 按地址做双向存储转发，TH 实现本机版本/PING 响应；再实测 AP→MC→TH→MC→AP 的 PING/PONG RTT。该结果证明通信测时，不替代后续温度/状态业务验收。

VMware/远端在当前环境仍受 socket 限制；不妨碍本地协议开发准备，影响真实串口联调和服务器同步。首轮硬件先收集 RTT 分布和错误数据，不自拟已接受的时延上限。

当前建议下一张票为 **V2-P01 最小契约与样例预期**，随后做接口和编解码；已有工程核验无需重复。正式任务卡的状态、Reviewer 和资源需要如实登记，本计划没有自动将它们改为 Ready/Done。
