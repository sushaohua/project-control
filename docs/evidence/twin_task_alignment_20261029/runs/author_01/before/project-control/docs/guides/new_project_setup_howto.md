# 新项目搭建 How-to：从目标到可验证交付

日期：2026-10-28｜状态：经验草稿，待独立 QA 审阅

本文提炼 AP–MC–TH 项目的实践，适用于多仓、嵌入式或软硬件协同项目。具体工具、门禁和硬件参数应按新项目裁剪；不要将本项目的地址、版本、协议或验收结果直接当作新项目事实。

## 1. 确定目标与边界

1. 用一页写清用户目标、使用环境、关键约束、非目标和第一个可演示结果。例如先完成一次真实设备查询，再扩展业务功能。
2. 建立输入登记：需求、现有源码、硬件资料、工具链及来源；分别标识用户确认、代码推断、实测和待确认。将关键资料保存在项目可访问的位置。
3. 记录决策、负责人、日期和影响范围。设计草案、已冻结契约、实现和验收分别标记状态，避免历史文档与当前事实混用。

产出：项目入口 README、需求与决策基线、风险及待确认清单。

## 2. 组织仓库和可恢复环境

按团队和交付物划分源码、项目控制和独立测试资产；只有确有多仓需求时才引入入口仓与版本清单。明确每个仓库的职责、分支、提交版本与权威规则位置，记录构建依赖、硬件和环境变量。不要提交凭据、构建缓存或本地绝对路径。

本项目用入口仓、四个独立仓库和 `workspace.json` 锁定恢复提交，不使用 submodule；这是一个可选方案。先分别提交子仓，再更新入口锁文件；恢复到空目录并验证版本。锁文件描述可恢复快照，不代表集成验收。操作例子见[工作区说明](../../../WORKSPACE.md)，应先把 URL、仓库及权限改成新项目实际配置。

## 3. 先冻结最小端到端契约

画出节点和责任边界，选择一条贯穿所有必要节点的最小业务链。针对链路写明：

- 连接、速率、信号方向、节点身份及环境前提。
- 请求和响应格式、字段语义、长度、版本、校验、路由、超时与错误处理。
- 数据所有权、队列与资源上限、谁生成响应、失败和恢复行为。
- 正常与异常验收条件，以及接口变更如何影响各端。

对照契约同时识别各节点、部署与测试工具的必要工作。历史上本项目出现中间节点代替下游生成响应，导致局部成功无法证明真实端到端能力；因此中继和目标节点必须分别明确职责。示例见[只读级联 ICD](../interfaces/ap_mc_th_readonly_cascade_icd.md)和[候选裁决](../decisions/cascade_candidate_adjudication_20261027.md)。

## 4. 拆任务并实现

按可交付能力拆分任务，卡内写清输入版本、负责范围、依赖、输出、验收标准及证据位置。一个模块内部的小步骤可用检查点，跨节点接口、共享写路径及硬件资源需明确依赖和排他关系。角色名称或计划中的会话不是实际执行或签署。

按契约实现各端，优先复用经过确认的存量能力；新增嵌入式代码按项目的函数规模、参数、内存、指针、超时和寄存器规范执行，继承代码保持最小必要差异。按风险先构建和执行软件测试，再进行实物装配。任务完成后记录准确源码版本、构建命令、工具链、产物哈希和未覆盖项。

## 5. 分层验证并交付

1. **准备独立预期**：依据契约准备正常、异常、边界向量；测试工具本身也需独立审查。
2. **软件验证**：编译、单元测试、协议向量及模拟传输分别记录命令、版本、输出和退出码。
3. **装配和联调**：固定各端候选及部署方式，核对板卡身份、供电、接线、串口和固件；记录问题与修复后的版本。
4. **独立验收**：独立审查者按预先接受的条件复验，真实硬件要求下采集设备路径、配置、时间戳、原始收发和异常恢复证据；明确任何未直接采集的链路。
5. **收件和交接**：对照准确候选汇总通过、失败和未覆盖范围，保留原始日志及历史结论；更新任务状态和恢复清单，留下一位新接手者可执行的下一步。

本项目的独立 QA 必须由独立 Codex 会话执行，作者自检不能代替；QA 自身产物还需独立复核。完整要求见[独立 QA 规则](../../.agents/rules/codex_qa_review.md)。新项目应明确采用的独立性和硬件门禁，并按实际条件安排人员及设备。

## 6. 启动清单

- [ ] 目标、最小交付、非目标和验收标准已记录。
- [ ] 仓库职责、规则权威位置、恢复方式及准确版本可查。
- [ ] 接口、硬件输入、各节点责任与失败行为已确认。
- [ ] 任务依赖、写入范围、执行者和独立审查安排明确。
- [ ] 构建、软件测试、真实台架及证据要求分别列明。
- [ ] 每次交付绑定版本和产物；未完成项及下一步可追溯。
