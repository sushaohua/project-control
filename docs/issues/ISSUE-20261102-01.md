# 缺陷报告: 新机引导向导 (OOBE) 版本未探测与工作台导向闭环缺失

## 1. 缺陷概述
在真实 VMware Twin 环境与真实物理双板卡台架（MC AT32F435 + TH AT32F423）连接正常的条件下，启动 Web HMI 进行新机自检向导（OOBE）操作。向导 Step 3（微控制器固件通信自检）未触发底层版本探测，固件版本及状态永久滞留在占位状态“未就绪/未读取”，且 Step 5“进入打印控制台”未完成工作台导航与 Toast 交互闭环。

## 2. 真实硬件调用链审计证据
1. **真实硬件直接通信核验**：
   通过上位机 CLI 独占串口 `/dev/ttyUSB0` 发送 MiniMCProto v2.0 `CMD_GET_VERSION (0x01)`：
   - MC (Target 2): 耗时 7.61ms，正确返回 `proto_ver: 2.0`, `firmware_ver: 1.0`, `boot_id: 0x01020304`, `git_commit: 0xA6791332`。
   - TH (Target 3): 耗时 13.33ms，正确返回 `proto_ver: 2.0`, `firmware_ver: 1.0`, `boot_id: 0x8877AA55`, `git_commit: 0x6356C05A`。
   证明双 MCU 硬件健康、固件版本完全支持契约。
2. **微服务集群链路核验**：
   - `aisoc_forward_service` 启动后仅轮询温度遥测帧 (`CMD_QUERY_TEMP`)，未集成启动版本探测或按需版本探测。
   - `aisoc_device_manager` 在启动初始化时将 `mc_ver.is_valid` 和 `th_ver.is_valid` 默认置为 `false`，且由于缺乏版本更新消息，快照中始终返回 `valid: false, status: OFFLINE`。
   - Web 前端 `app.js` 收到 `valid: false` 后将状态退化为 `UNKNOWN`，呈现“未就绪/未读取”。
3. **前端交互契约审计**：
   - `app.js` 中 `btnOobeFinish` 点击处理函数仅隐藏弹窗，未调用 `switchTab('tab-dashboard')`，未触发 Toast 提示。

## 3. 关联任务与派发计划

  - `ENG-UI`：负责 `app.js` 中向导完成事件的工作台路由导向与 Toast 闭环。
