# v2.0 首批任务的执行、验收与回溯约定

2026-10-28 起未执行任务的粒度、角色分配、当前只读级联联调顺序以[执行复盘与重排](../planning/workflow_replan_20261028.md)为准。下列 V2 原子拆分是已完成批次的历史方法，不再要求后续工作按函数、符号桩和构建阶段逐张交接；独立预期、实际版本和真实 HIL 的门禁继续适用。

## 范围与权威位置

本约定覆盖首个AP离线协议增量，并与[有效任务索引](../../.agents/kanban/microtasks/minimc_v2/README.md)、[任务卡模板](../../.agents/rules/templates/任务卡模板.md)、[派单提示词](../../.agents/rules/templates/角色任务提示词.md)一起使用。模板与本约定只定义流程，不指定当前实际COORD、作者或正在运行会话；这些身份及反馈方式以准确任务卡和实际交接记录为准，旧会话记录保留其历史时间。

任务原件位于控制仓`.agents/kanban/`。V2原25张拆解后有6张移入superseded并由V2-P0506承接，2026-10-27目录采样为20张有效V2微步卡；后续数量、状态和替代关系只读准确卡片，本指南不是实时投影。任务索引/看板仍可能有旧投影，派单先核原件与替代关系。每张实际票只有一个primary_work_package；旧分组及已替代卡不直接派单。

本批是离线编解码/组帧能力，不包含AP串口事务、MCU协议实现、OTA、物理急停或HIL。当前离线候选归档票为V2-P0506；原V2-P06B/P06C已替代，只保留历史来源。MS-05/07/11/17的固件/实测条件不因离线通过被解除。跨节点纠偏按[完整实施方案](../planning/ap_mc_th_cascade_recovery_implementationplan_20261027_162003.md)建立相关能力/验收票，不把该方案文档审查当成源码或硬件通过。

## 每票怎样进入 Ready

卡内 `source_baseline` 是规划时已观察的代码快照；后续前置代码尚未产生，不能为它们编造 SHA。因此 `base_commit`、`dispatch_binding` 和每项 `dependency_conditions.accepted_version/acceptance_evidence` 在派单前按实际结果解析填写。设计首票可以从问题和本地原稿开始，不要求它将产出的契约在开工前已经存在。

在当前有效用户授权内，由实际 COORD 逐票落实：

1. 指定实际作者及与作者不同的必需检查者，写入会话入口。作者、QA 作者及其 Reviewer 都不能对自己的交付独立签署；岗位名称不是会话。
2. 绑定本地协议 SHA256、实际源码 HEAD、开工差异摘要、各前置的已接受产物版本及可使用条件。只有 Done 而没有相应能力证据，不满足 Ready。
3. 将相对 `write_scope` 映射到实际工作区。卡内路径一律为“仓库名＋仓内路径”，或 `write_scope` 的“仓库→仓内路径”形式；新文件可以尚不存在，真实仓库和父范围必须存在。源码修改在派单时登记隔离检出/分支或等效独占安排，代码提交不得跨仓混合。
4. 指定实际资源/输出目录、有限预算和人工占用期限 `lease`；租约不是工具锁。卡中 30 分钟是进度检查点，不是完工承诺。到检查点交实际进展，未续领不继续新增改动。
5. 明确本票命令、正常和异常判据、输出位置和实际收件方，作者回执后方可开工。卡中 `planned-output` 命令只在相应前置产物创建并接受后运行，不是本轮已执行证据。

未来验收命令中的 `soc-ap/`、`test_harness/` 相对于实际执行工作区；独立检出使用相同四仓布局，或在派单修订中记录准确路径映射。不得隐式跳回知识库。资源冲突时串行；当前不需要部署调度服务。

检查方式：

```bash
# 从工作区根目录执行；工具依赖当前已安装的 PyYAML，只用于任务管理。
python3 project-control/tools/check_task_graph.py --workspace .

# 检查某票是否具备派单字段；未满足时明确非零退出，不会自动修改状态。
python3 project-control/tools/check_task_graph.py --workspace . --check-ready V2-P01A
```

静态工具通过只表示它实际覆盖的结构/字段检查通过。2026-10-28 所见工具已扫描多个微步目录，并实现部分状态/租约/路径检查；旧版缺陷不能直接当成当前全部缺陷，报告内容、签署适用范围和准确候选仍需实际核对。模板新增字段不会自动变成工具能力，现有接受证据与工具覆盖由 CR-12 对账；需要补验的部分单列，不重复全部已通过检查。

## 逐票输出和失败处理

每票的证据根目录已在卡内固定为 `docs/evidence/minimc_v2/<task-id>/`。真实执行时再创建唯一 `runs/<actual-run-id>/`，run ID 用当次可定位的时间/会话标识记录，不回填假历史。每次失败、更正、重跑保留原文件；没有运行的命令写“未执行”，不用预期值充当实际结果。

## 代码编写规范与硬性门禁

代码实施必须无条件遵从 [C/C++ 编码规范](../../.agents/rules/c_cpp_coding_standard.md) 及主约束总纲硬门禁：
1. **函数规模限制**：**严禁编写超过 50 行的自研非结构体函数**。复杂逻辑必须拆解为带 `static` 修饰的内部辅助函数；
2. **入参个数限制**：**严禁编写超过 4 个入参的自研非结构体函数**。超过 4 个参数者必须封装为专用结构体指针；
3. **存量代码豁免原则**：自研新增代码 100% 严格执行；第三方存量代码以最小修改预算（Minimal Diff Budget）优先；
4. **内存与指针安全**：指针显式化（禁用 `*dst++ = *src++` 等压缩黑魔法，指针解引用独立成行，深度 $\le 2$），零动态堆分配（禁止 `new`/`delete`/`malloc`/`free`/动态 STL），禁用异常体系与 RTTI；
5. **防御性检查与控制流**：对外公开函数首行优先做空指针防御检查（Guard Clause），函数大括号嵌套严禁超过 3 层，禁用嵌套三元运算符；
6. **硬件操作与轮询安全**：寄存器读-改-写分步执行（Clear 后 Set），硬件轮询等待必须带超时计数退出保护（严禁 `while (!FLAG);` 死等），严禁裸魔数。

每次实际 run 至少保存：

- 开始/结束时间、实际作者、任务 ID/revision、租约和工作区；准确协议/源码/前置版本及工作区差异。
- 命令、cwd、实际环境/工具、退出码、完整 stdout/stderr、告警和非零用例数量。
- 本次 diff、候选 commit 或完整 diff＋SHA256、产物摘要、哪些能力已实现/仍未实现。
- 原始错误→查证根因→本次纠正→重跑结果。首次失败即停止后续步骤；最多两次有依据的纠正仍失败则停止，保存检查点交回。
- 独立检查的实际会话、所审同一候选版本、结果/限制、收件回执；没有这些结果时保持空值/待检查。

报告模板见 [task_run_record.md](templates/task_run_record.md)。日志/报告是输出，不允许执行者改正式任务状态。只撤回本票差异；禁止全仓 reset/clean、覆盖用户原有修改或放宽检查获得绿色结果。接口或预期确需改变时修订卡并重新接受相关输入，旧结果只对旧版本有效。

## 独立检查与关闭

用户 2026-10-26 明确要求：后续独立 QA 统一使用 Codex。包括 QA Reviewer、QA Verifier 和 QA 作者产物的独立 ARCH 复核，均遵守 [Codex QA 规则](../../.agents/rules/codex_qa_review.md)。已完成的 P01A/P01B 及原始报告保留原会话，未完成卡引用该规则；作者、其他岗位和硬件条件保持原有分工。

派单时读取 `qa_review_policy`，按条目 `platform: codex` 选择独立 Codex。未启动的任务只登记 `planned_session_alias`，实际 `session` 保持 null；落实会话后由 COORD 填入可定位标识。旧卡保留历史计划别名（如codex-qa-session-01）；实际是否已审核只看对应准确版本的session/报告，不由本指南写实时结论。通过 CLI 运行时保存真实会话 ID 与别名对应关系。结构工具不负责启动 Codex，未接调度脚本时采用主会话启动或人工转交。

独立审查必须核对协议原文、准确交付物哈希与实际日志。报告保存所审版本、真实命令及退出码、过程/结果判据、限制和 APPROVED/REJECTED；COORD 收件并核对候选与报告哈希后再推进状态。退出码 0、报告存在或结构检查通过不能代替签署通过；失败、超时或缺失报告不得释放下一微步。

每张卡的 Reviewer 为必需项。QA 编写独立预期或运行器时，其报告仍由非作者检查。实现作者不能改 `test_harness` 中独立预期促通过，QA 也不能改业务代码促通过；本规则目前由人工核对执行，不声称已有文件系统权限系统。

`Review → Verify → Done` 必须绑定同一准确交付：内容/运行检查结论齐全，实际 COORD 确认收件，代码适用时绑定消费/集成版本。代码实现票的“验证通过”只表示该原子能力；当前V2-P0506承接原V2-P06B/P06C的复现/归档范围，是否满足全部必需检查仍按其准确候选证据核对，不因合票自动视为接受。Done 后再变更接口或代码，按新 revision/复验记录更新适用关系，不能沿用旧通过。

## 首批工具、样例与覆盖范围

P01C 只写独立样例 JSON，P01D 另实现只依赖 Python 标准库的参考校验器；样例数据与参考算法也分票。样例需有 `schema_version`、协议 SHA256、唯一 `case_id`、分组、固定输入和预期；V04 明确为帧结构有效但急停业务长度冲突，不作为合法急停执行样例。

P02C 单独冻结测试探针 CLI/文本输出与运行器接口；不引入外部 C++ JSON 库，也不改变线缆格式。P03D 探针仅适配生产 API，参考算法由 `test_harness` 保存，禁止探针自算一份期望使自身实现被自己验证。

分组为：独立 `reference`，以及 `crc`、`encode`、`decode_bounds`、`decode`、`stream_sync`、`stream_header`、`stream_payload`、`timeout`、`recovery` 九个功能组。`stub` 只在桩阶段检查显式未实现；`all` 仅汇总九个功能组。最终 CTest 注册十个 `minimc_*` 检查（reference＋九功能组）和原 `host_runtime_smoke`，合计十一项；不能登记会在完成实现后仍期待未实现的 stub，也不能靠重复 all 充当独立覆盖。

每组必须实际执行非零 case。编码对固定字节期望比较；解码对独立字段期望比较；流式测试注入分片、噪声、错误和模拟时钟，不靠真实 sleep。50ms 使用规范的 `>50` 判断，覆盖 49/50/51ms 与 uint32_t 回绕；不据此设请求期限或 RTT 门槛。

显式传入 `MINIMC_QA_ROOT` 后缺参考脚本/样例必须配置失败；没有传入时允许仅构建 AP/库，但必须显示协议测试未启用，不能以 host smoke 1/1 冒充协议候选验收。PyYAML 仅用于控制仓任务检查，不进入 AP 程序依赖；工具缺失如实报错，不自动安装包。

最终候选 YAML 必含 `candidate_id`、`scope`、`repositories`（准确 commit/diff/hash）、`protocol`、`verification`（报告路径/哈希/所审版本/会话）、`limitations`、`handoff`。候选归档不能只写“各仓最新分支”，不能把文档中的预期或本批静态结构检查写为已发生的独立验收。


## 模板接入与状态推进核对

新建卡登记template_version=2026-10-27；存量活动卡在本轮revision补必要字段，历史报告和签署不批量回填。parent_task/coordination/inherited_gates记录关联，相关前置能力必须显式落实到depends_on与对象化dependency_conditions；不得把最终HIL通过反向设为单板实现开工前置。

Ready确认blocked=false、前置能力及准确接受版本、owner/session/worktree/范围/授权/资源、有效租约和预算；本票候选与最终签署在交付后产生。Review/Verify/Done分别核同一候选、全部必需独立审查、适用运行/集成与COORD接受，收到不等于通过。不适用环节列理由与依据，不能用默认单板/默认通过跳过检查。

运行记录逐命令/逐例写独立预期与实际观察，计划和实际分开；必跑测试名/组与非零case明确。正常查询零有效关联响应失败，预期断链/坏帧无响应可通过相应负例；不混淆CRC、命令语义、事务匹配、物理闭环。文档票核结构、来源和链接，不伪造构建或HIL。独立签署用[QA报告模板](../../.agents/rules/templates/QA审查报告模板.md)。

输入变化或旧误判时追加evidence_updates/撤回记录，标明旧/新候选、受影响消费者和恢复条件，保留历史原件。正式status保持Backlog/Ready/InProgress/Review/Verify/Done；报告decision使用APPROVED/REJECTED，阻塞用blocked和recovery_condition。全部正式变更由唯一实际COORD完成，模板修改不自行改变现有任务状态。
