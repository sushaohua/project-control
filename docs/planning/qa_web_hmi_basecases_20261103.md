## 1. 来源与用例冻结

本专项采用的策略须在任务卡明确：新卡 `qa_policy: streamlined-v1`，单轮独立 QA 审查代码和功能/回归证据；QA 自编用例/预期/工具须非作者独立检查，不递归增加报告复核。未迁移旧卡保留 legacy 门禁。

basecase 覆盖手册 9 类功能及 7 阶段用户旅程，PM/ARCH 将每项映射至正式需求/准确 revision 和接受依据，独立 QA 据此细化自动化。未接受或不稳定的手册描述先作为候选 base，不能仅凭手册存在认定已稳定实现。产品范围内缺功能记失败，需求歧义阻塞相关断言，冻结项说明依据，禁止失败后删项。

手册仅用于用户动作与预期线索，以下不直接作固定黄金值：地址、版本/短 hash、示例温度、模型层数、5×5 具体高度、HMS 示例错误码、按钮选择器、所谓“瞬时/毫秒级”及“零风险”描述。预期来源顺序为实际用户批准/现行正式需求、已接受契约及适用工程门禁，再与手册对账；冲突记录澄清，不以当前实现输出倒推正确答案。

执行前必须解决或登记以下来源差异；有明确高层门禁的先遵守门禁，额外产品承诺交 PM/ARCH 确认：

| 澄清项 | 观察与处理 |
| --- | --- |
| 断线 CPU | 手册功能 9 写 ≤1%，现行工程门禁为 ≤2%；测量口径/进程/采样窗口同样待冻结。保留两者来源，产品是否承诺更严阈值由 PM/ARCH 明确，不静默替换 |

| 作业进度 | 手册“匀速旋转”不能覆盖硬件 ACK/执行推进规则；用例校验真实执行依据、暂停/断线停止与最终完成，不接受本地计时器假进度 |

每例冻结：`case_id/revision`、`suite`、需求/手册章节、角色、起始页面、前置数据及依赖、逐步操作/预期/期限、正常/故障/恢复、物理效果和证据、失败处理及复位。未给出期限的字段由契约补齐，相关时限断言保持待明确。

### 2.1 串口采集与逐例核对方法

真实 MC/TH Debug 串口日志是涉及固件处理的主要检测证据；Web/API 结果及物理观察是同一请求的随附对账证据。三者必须一致才可 PASS：串口日志不能单独证明真实动作，UI/API 不能证明固件收到请求；可见的 UI 或物理结果明确不符即 FAIL。适用物理证据缺失时该 HIL 范围保持未执行/阻塞，不能把动作标为完成。

| 链路 | 主机与连接 | 参数及识别 | 采集约束 |
| --- | --- | --- | --- |
| AP↔MC 业务 UART | VMware Ubuntu 上运行 AP；动态确认所用业务串口 | 按方案核对 `921600 8N1`、设备/固件和端口归属；不从设备名猜身份 | 保存本轮真实双向原始帧及收发时间；不另接读者争抢该业务串口 |
| MC↔TH 级联 UART | MC 与 TH 板间物理线 | 按方案核对 `921600 8N1` 和两端角色 | 以业务路径产生的真实转发/应答及两端 Debug 佐证；不强制另接读者抢线 |
| MC Debug | Windows 宿主动态枚举 COM 设备 | 按 `[MC-DBG]` 特征识别实际端口，核对端口 UID、探针/设备身份、固件及角色；`115200 8N1` | 保存从启动前开始的原始字节流、端口映射和采集状态 |
| TH Debug | Windows 宿主动态枚举 COM 设备 | 按 `[TH-DBG]` 特征识别实际端口，核对端口 UID、探针/设备身份、固件及角色；`115200 8N1` | 保存从启动前开始的原始字节流、端口映射和采集状态 |

Windows 侧物理工具环境、探针与串口操作遵守相关仓规则和本任务已批准环境。执行者须先核对主机、工具/解释器、设备 UID、固件版本及端口角色；若实际连接与清单不符则不开始动作。串口采集应先于服务冷启动、板卡冷启动及用户动作启动。每个 run 使用新的只追加源文件；禁止覆盖、拼接、重排、补写伪造日志。记录主机时钟来源与偏差；每次重启记新 boot epoch，序列号只在同一 epoch/目标节点/命令语义内关联。明确记录丢字节、截断、缓冲溢出、采集断档及其发生时间/链路；不得把采集缺口归因为设备未执行，也不得以补造日志恢复完整性。

每个动作在采集器旁路记录 `case_id`、`action_id` 与动作时间，不将其扩展成业务协议字段。用已接受 ICD/schema 中的请求/响应关联规则，逐项核对目标节点、序列号、命令、实际载荷（或安全的载荷指纹）、请求与响应，以及相关节点的 RX/RELAY/STATE/TX；另保存对应 HTTP/API 请求、返回和 UI 观察。不要只 grep `ACK`、`DONE`，或因字段存在即通过；核验载荷确属本次操作、状态变化有新鲜来源且响应与该请求匹配。序列号回绕、复位/重新上电、时钟偏差和旧缓存均须分段处理，禁止跨 boot epoch 或不同 target/command 错配。具体 dir/cmd/字段/单位以本轮已接受 ICD/schema 为准；整改计划中的日志行、HTTP 参数和数值均是示意，不是固定黄金值。若计划描述与接受契约或授权边界冲突，记录来源并在执行前由相应 Owner/ARCH 对账，不由测试作者自行裁定。

正常对账窗口按参考方案核对 `drop=0`、`trunc=0` 及采集连续性；日志/关联信息缺失、格式歧义或采集断档导致不能判定时，记录证据不足和解除条件，不报 PASS，也不把采集失败直接判作业务失败。DELTA-DBG/COMB 的故意慢读、满缓冲或关闭 Debug 子例另记：允许预期的显式丢失/关闭，以业务时序、故障提示及恢复证据判断该负例，不要求故意关闭的日志仍完整输出。采集器、解析器或自动化尚未具备时登记工具缺口；本文描述不代表工具已经实现。

#### `[MC-DBG]` / `[TH-DBG]` 闭环证据

涉及固件的用例按下表核对调试口原始日志，并在结果中引用原始文件及行号/字节区间。箭头表示同一事务的因果关联，不规定跨主机时间戳严格递增，也不要求不同命令使用同一个序列号；具体事件名和关联方式以已接受契约为准。

| 场景 | 必需的调试口闭环证据 | 核对重点 |
| --- | --- | --- |
| MC 本板处理 | `[MC-DBG] RX` → 实际处理/采样或执行状态 → `TX`，再与 AP 收到的匹配响应对账 | 请求内容、结果及错误码一致；未涉及 TH 时不要求 `[TH-DBG]` |
| TH 经 MC 级联处理 | `[MC-DBG] RX → RELAY_TX` → `[TH-DBG] RX → 实际处理/采样或执行状态 → TX` → `[MC-DBG] RELAY_RX`，再与 AP 收到的匹配响应对账 | 端到端目标、命令、载荷和响应关联成立；若中继转换序列号，记录既有映射；仅 MC 转发或本地返回 ACK 不算 TH 闭环 |
| 异步动作完成 | 受理请求/ACK → 真实执行事件 → 新鲜完成状态或后续查询响应，关联同一动作/作业 | 入队、受理 ACK 与执行完成分开；完成日志须来自真实执行路径，并与适用物理效果、Web/API 结果核对 |
| 只读查询/遥测 | 对应节点的新采样/实际状态 → 真实上报/响应 → MC 转发（若适用） → AP/UI 同样本 | 核对来源、有效性及新鲜度；不要求无关动作或物理跃迁 |
| 故障与恢复 | 记录实际故障层；对应节点/链路的超时或错误 → 降级；恢复后重新出现完整成功链路 | AP↔MC 断链时可由 AP 超时说明，不能强求断链后 MC 收到请求或 TH 报错；恢复不能复用旧 ACK/样本 |

上述日志用于确认通信与固件处理闭环；声称运动、回零、调平、供料等物理完成时，仍核对原有物理效果要求。只有 `[MC-DBG]` / `[TH-DBG]` 前缀、启动信息、心跳或孤立的 `ACK/DONE`，均不构成相应业务闭环。

## 3. 三个核心用例的逐步规格

下面的 `T_probe / T_sample / T_save / T_nav / T_recover` 等为待绑定契约的期限键，不是脚本默认常量；未接受时不能运行相应时限断言并宣称通过。完整自动化需将其余规格组同样展开，不能用组表代替逐步 case。

| case / 前置 | 用户步骤 | 逐步预期与期限 | 失败/恢复及证据 |
| --- | --- | --- | --- |
| BASE-02-POS；干净 profile、MC/TH 健康，本轮采集在服务冷启动前开始 | 首页→新机引导→下一步→语言选择→设备检查 | 用户可实际点击；触发/取得本轮真实探测，在 `T_probe` 内分别显示两板版本和 ONLINE，AP 同步状态有依据 | 超时 UNKNOWN 记 FAIL，保存 UI/启动/真实 TX/RX/调试日志，提交 Issue；相关后续阻塞，独立例继续 |
| BASE-02-NEG/REC；单独的清洁运行状态 | 未接设备打开同一检查页→确认未就绪→按 SOP 接回设备 | 离线不全绿；重连在 `T_recover` 内发生新探测、版本及在线恢复，旧缓存不满足断言 | 物理动作保留操作者/时戳；恢复失败保留现场，不能在浏览器注入版本 |
| BASE-05-POS/REC；前四步真实满足 | 总结页→完成→观察工作台→刷新→重新打开向导 | `T_save/T_nav` 内反馈/导航；完成标志按契约保持，重开入口可用且不丢用户配置 | 任一无反馈/无导航/未落盘记相应失败；保留点击轨迹、公开返回与刷新结果 |
| BASE-20-POS；温度传感器健康，确认源节点/单位 | 首页→点击温度胶囊→温度面板→观察至少约定数量的新样本 | 在 `T_sample` 内按同一采样关联原始值和 UI，正确换算/舍入并标有效；两板版本独立匹配 | 不使用手册 120.7/24.5 作固定预期；保存采样关联、帧和 UI 读数 |
| BASE-20-NEG/REC；授权故障窗口 | 按 SOP 使一端数据失效→观察→恢复来源 | 按契约失效、锁定相关控制并提示；新有效样本恢复，旧温度不仍显示 FRESH | 记录故障层/持续时间/恢复；加热继续 0%，不为造温度实加热 |

## 4. 首轮增量 delta

| 组 | 正常必测 | 相关故障/恢复和回归 |
| --- | --- | --- |
| DELTA-DBG | UI 发 MC 指令，对应 MC 实收/处理/回复；UI 发 TH 指令，关联 MC 中继和 TH 本板；温度实际发送与 UI 同样本对账；两路调试输出有方向/来源/结果 | 开关调试、拔调试线、慢采集/满缓冲；丢失显式可见，业务不阻塞；分别验证调试关闭/开启及必要 BASE-02/10/20/24 |
| DELTA-BAUD | 确认 VMware/AP 与 MC 两端真实使用 921600，版本/温度/适用运动和作业正常；按冻结频率/时长统计 CRC/丢帧/超时/资源 | 速率不匹配的明确失败、重连/重启和恢复；升级路径兼容按批准范围验证；MC↔TH 和调试 UART 参数单独核对 |
| DELTA-COMB | 同一最终候选上 921600＋两路 Debug 同时工作，通过 UI→设备→UI 主旅程 | 批准负载下日志带宽不足时显式丢失计数，业务满足原时序；不拿缺日志当设备未收到；回归暂停/取消、失联和恢复 |

以上是三组 delta 的验收规格，不表示两项功能或自动化已经交付；冻结后逐项编号、接受并映射脚本。

## 5. 执行与批准边界

按[交付门禁 §4.2](../../.agents/rules/delivery_and_coord_gate.md#42-软件与真实hil双门禁及批准范围2026-11-02)在每个实际 case 的现有前置、预期、证据和结果记录中明确层级；不增加机器字段，不因 Mock/PTY 用例通过而填写真实 HIL 通过：

| 用例范围 | 最终接受要求 |
| --- | --- |
| BASE-01/02/04/06 中的真实探测、硬件状态与传感器断言；BASE-20/21/24/25 | 必需真实 HIL，核对实际节点响应、采样/身份或物理故障及恢复；不能用缓存、模拟器在线或生成的日志代替 |
| BASE-07、BASE-10～16 的实际急停、作业、运动、回零、调平断言；BASE-18 的实际通道生效 | 必需真实 HIL 与适用物理效果；真实接收、执行完成和效果分别核对，逻辑坐标/进度变化不独证动作 |
| DELTA-DBG、DELTA-BAUD、DELTA-COMB 的最终功能接受 | 必需真实 HIL，在锁定组合上关联 Web/API、真实业务帧、所涉节点 Debug 和测量/效果；921600 业务链路与调试、级联链路参数分别核实 |
| 语言/主题、导航、文件解析、配置保存等纯软件断言 | 可在声明的软件范围内接受；不能据此接受涉及的真实动作、设备健康或完整硬件用户旅程 |
| BASE-23 的设备告警，以及 BASE-26/27 等含混合前提的场景 | 按具体断言映射：声称真实设备健康、硬件故障或恢复的部分必需 HIL；纯浏览器/服务故障部分可独立软件验证，不能相互替代 |

正式用例冻结时由 PM/ARCH/相关 Owner 按已接受范围确认上述映射，QA 细化步骤和采集点；纯软件子断言通过不能把同组的物理断言标为不适用。已有台架临时不可用或采集工具未接通时，保留相应 HIL 阻塞和解除条件，不删必测项；原独立软件结果继续保留。

HIL 每例关联真实入口结果、匹配业务帧、对应节点 Debug 与测量/物理效果；非 Web 或未涉及节点的适用性事前明确。查询类核对实际来源及样本一致性，不强求物理跃迁；运动等动作类使用适用反馈或现场观察。正负与恢复走同一实际路径，旁路构造日志不作为运行证据。

首次完整轮对全部适用基础范围和本轮 delta 制定非零必测清单；正负及恢复分别计数。按软件自动化、真实 HIL、UI 人工可执行性记录结果。采用本轮锁定的实际版本/数据，不预填 PASS、MATCH、RTT 或在线状态。

运动/供料/回零/调平需要已确认限位、实际效果观察和独占窗口；无相应物理能力时该范围保持阻塞，不把逻辑 ACK 升为物理完成。现有手册没有覆盖的已接受首版功能仍应从正式需求补充，不能把本清单当成首版全部需求的替代。
