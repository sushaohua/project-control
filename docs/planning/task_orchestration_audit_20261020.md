## 2. 需要修订的编排内容

1. **把新协议路线纳入现有任务，而非另开一套无关联计划。** 例如 MS-05 原卡仍写“D20 原二进制稿继续为依据、迁移选择待确认”，与最新 B0 已采用本地 v2.0 不一致；需修订受影响卡的输入/目标/能力条件，并保留版本变更依据。主控基础、双端、业务查询验收仍分别保留，不能用离线库测试代替 HIL。
2. **把首批 P04/P05 继续拆开。** 建议 CRC、编码、解码分别成票；解析器接口、同步/头部处理、载荷/CRC 收尾、字节超时与复位分别成票。头文件接口、链接桩、业务实现按已定微步规则分阶段，避免同票横跨 API、驱动和业务。
3. **独立测试预期先于依赖它的实现。** P01 应提供正常和边界预期；P06 是独立复核/汇总阶段，不能等所有实现写完再倒推唯一答案。每一实现票仍需自己的最小有效检查，不能统一拖到最后。
4. **区分设计前置与实测接受前置。** 已选 v2.0 可支持离线最小契约设计；MS-05 的硬件样例接受仍依赖真实证据。应明确哪张微步产出离线设计，哪张卡接受实际固件能力，防止把二者混在一起形成等待。
5. **将未决项限制在受影响范围。** V04 急停载荷冲突阻止其业务实现接受，不阻止无关 GET_VERSION/PING/PONG 和结构层工作；请求级期限/重试策略未明确时不能直接进入会话实现。协议的 50ms 是字节间超时，不是 RTT 通过线。
6. **落实当前批次的检查与交接。** 在现有授权内登记实际作者、独立 Reviewer/QA 和收件方；无法落实的字段保持待安排，不能填虚构身份、签署或 ACK。

## 3. 每张开工票应具备的闭环

以下字段应落实到**实际任务卡**，不能只写在通用模板中：

| 环节 | 具体要求 |
| --- | --- |
| 输入 | 上游交付、协议/源码准确版本或哈希、工作区差异、该输入的可使用条件；未知项和本票非目标明确 |
| 动作 | 一个明确结果，真实仓库与文件白名单，阶段/接口边界，实际执行者、资源/输出目录和占用检查点 |
| 判据 | 可执行命令与 cwd、正常及相关异常预期、明确通过/失败条件；未创建的测试目标必须标为待实现 |
| 证据 | 命令、环境、开始/结束时间、退出码、完整日志、输入与候选 commit/哈希，关联任务 ID/revision |
| 失败 | 原始错误、查证根因、每次纠正与重跑记录；重试限额和停止条件；按本票差异回退并保留用户原有改动 |
| 检查 | 不同实际执行者对同一候选版本给评审/QA 结论；作者测试与独立检查分别记录 |
| 交付 | 实际收件方、交付路径和回执；适用时记录合入版本与集成检查，之后才由 COORD 更新状态、放行下一票 |

代码、文档、构建、HIL 分别使用相应证据。调查否定结果可以完成调查，但不能自动让依赖该能力的实现 Ready；过程闭环不等于每次都必须成功。

## 4. 回溯已经具备什么，还缺什么

已经具备：代码仓的现有 Git 历史、MC/TH 实际 HEAD 与部分源码/配置/制品 SHA256、本地协议原稿及来源校验、AP 构建/迁移运行日志、协议算术预核对和网络失败原文。这些能够复核部分输入和观察结果。

尚未具备：本批文档/证据的已提交版本；逐票的候选 commit 或准确 diff/哈希；设计批准与实现起点的关联；失败→修正→重跑的连续记录；独立签署与所审版本的绑定；收件回执及后续卡消费关系。当前控制仓 HEAD 仍为 `97b17fb6842d708eccb4a96049c42f415cdbb15a`，本批新增/修改文件尚在工作区，不能说已进入 Git 历史或已同步服务器。

初期使用已有 Git＋Markdown＋原始日志即可。每票交付建立如下关联，不要求先开发新调度平台：

```text
用户决定/需求 → 协议与输入版本 → task_id + revision
→ 作者动作、diff/候选版本与原始日志
→ 独立评审/验证对同一版本的结论
→ 收件/集成回执 → 正式状态 → 下游引用该交付
```

文件哈希能发现内容变化，不能独自证明记录先后顺序、审批真实性或独立性；Git 提交也不能代替缺失的实际测试与评审。缺失项应记录为缺失，不事后补造。
