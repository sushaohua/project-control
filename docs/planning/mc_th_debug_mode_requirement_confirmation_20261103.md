# MC 和 TH Debug 模式需求确认及实施概要

## 1. 原始指令及理解

> 需要增加一个功能：MC和TF的debug模式。这个模式把主控发到MC和TH干的消息，MC和TH干上报的状态，在调试串口显示出来。这样可以用于问题拆分：发给MC的指令是否到了MC了。TH上报的温度是不是在UI正确显示了。用两个调试串口、用户UI，可以进行闭环验证。

本单按同条指令其余内容，将“TF”暂按“TH”、“主控”按 AP 理解，保留原文供用户纠正。用户目标已提出；以下日志边界和实施概要为建议，尚非已批准实现契约。

**一条需求：MC 和 TH 的通信调试模式。**开启后，MC 和 TH 各自在独立于业务链路的调试串口输出本板实际收发和处理记录。测试者将两个调试串口的记录与用户 Web UI 对照，定位指令下行及状态上行的中断或错误位置。一个需求可关联多个工程任务。

本单仅归档原文、整理需求和交接建议，不表示已入自动队列、创建正式任务、派发 Agent、实现功能或完成验收。优先级、是否纳入首版尚未指定，由 PM/COORD 结合用户范围决定；不擅自抢占现有任务。

## 2. 建议范围和日志契约

| 观察点 | 调试输出及用途 |
| --- | --- |
| MC 接收 AP 指令 | 在 MC 实际接收位置记录帧及校验/解析结果，证明字节到达 MC；有效命令的接收、拒绝、处理结果分别记录 |
| MC 自身状态上报 | 记录实际上报的状态、原始字段与单位、发送结果，供 AP/UI 对账 |
| MC 中继 TH 消息 | 若实际链路经过 MC，记录转发给 TH 及从 TH 收回并转发给 AP 的帧、方向和结果；保持既有透明转发语义 |
| TH 接收指令 | 在 TH 本板记录实际收到的指令及处理/拒绝结果，区分 MC 转发与 TH 真正收到 |
| TH 状态上报 | 记录温度等实际发出的状态帧、原始值、单位及有效性；区分生成、入队与真正发送/发送失败 |
| 用户 Web UI | 使用现有用户入口触发查询或控制，核对结果和温度等状态的转换、有效性、新鲜度与显示；本需求不默认新增 UI 控制页 |

建议统一记录：本板身份/固件标识、启动代次、本地单调时间、事件、方向、实际可用的命令/源目标/序号/长度、原始帧 Hex、解析结果及相关状态值。字段依据既有协议，不凭空假设所有报文都有序号；损坏或不完整帧只输出确实取得的字节和错误。

ARCH 与两端 Owner 冻结关联办法：优先复用现有请求序号和报文标识；无序号的遥测按已确认的载荷、采样/上报顺序及受控采集记录关联，无法唯一对应时明确标注。不同板的本地时钟不默认同步，不能直接相减宣称端到端延迟。AP 现有日志用于补足 UI 动作与业务串口之间的对应；不足时由 ARCH 明确有界依赖，不自动扩大 AP 改造。

日志语义必须区分“收到字节”“通过校验”“接受命令”“执行结果”“发送入队”“实际发送结果”。收到或打印一条指令不等于硬件已执行；TH 打印发送记录也不等于 AP 已收到或 UI 已正确显示。

## 3. 最小化和业务保护

- 优先复用既有调试串口及日志设施，默认关闭详细报文输出；不修改业务协议、Bootloader 或运动/温控保护逻辑。启停机制由 ARCH 核查后选择，不预设必须新增业务命令或 UI 开关。
- 调试串口与业务串口分离。调试线拔除、采集程序退出、串口慢或缓冲满时，业务继续按原契约工作；不能同步等待终端、不在中断或关键控制路径执行阻塞格式化输出。
- 采用有界静态缓冲及明确的 CPU、RAM、Flash、输出速率预算，避免动态堆分配和新增大依赖；关闭模式的占用、开启模式的最坏开销由 Owner 给出并验证，不在本单编造指标。
- 目标是在批准的业务负载内完整记录相关通信。若带宽或缓冲不足，必须显式计数并报告丢弃、截断和采集区间；不能静默抽样后声称“全部抓到”，也不能用不完整日志中未出现某帧证明设备未收到。
- 调试记录仅为观察，不注入测试指令、不改写业务帧、不以日志输出替代 ACK 或真实设备响应。

## 4. 验收场景和证据

先冻结实际板卡、两个调试端口的电气/引脚/波特率、业务链路、AP/MC/TH 候选及固件身份、Web 入口、关联规则、资源预算和完成期限。当前这些硬件与运行条件尚未核实；既有[联调 SOP](../operations/ap_mc_th_joint_debug.md)和[VMware 联调说明](../operations/vmware_twin_joint_debug.md)仅作查找入口，其中示例值不能直接作为本需求现场事实或黄金预期。

| 场景 | 必须看到的结果 |
| --- | --- |
| UI 发起一个已接受的 MC 查询/操作 | 对应 AP 请求、MC 本板接收/处理及真实响应、UI 反馈关联；实际完成与 ACK 按该操作原契约判断 |
| UI 发起一个已接受的 TH 查询/操作 | 依实际拓扑对照 MC 中继、TH 本板接收/处理、真实响应与 UI 反馈，能够区分每一跳 |
| TH 正常温度上报 | TH 发出的原始温度值、单位/有效性，经实际链路到达后台和 UI 后按既有转换及显示精度一致；关联同一采样，不能拿不同时刻数值直接比较 |
| MC 正常状态上报 | MC 调试记录、后台及 UI 对应状态一致，范围按当前已接受功能确定 |
| 目标断连、坏帧或超时，以及恢复 | 日志如实记录实际观察和故障，UI 按原契约降级；恢复后真实响应与状态恢复。故障注入由授权操作者按安全窗口执行 |
| 开关调试、拔除调试线、慢消费者及批准范围内高负载 | 原业务正常和时序/资源指标符合契约；日志缺失可见，恢复有明确行为，不锁死业务 |

保存两路调试串口原始采集、业务串口双向物证、后台关联日志、浏览器步骤/断言及时间记录，绑定同一轮候选和设备。温度读数对账证明传输和显示一致性，不独自证明传感器的绝对测温精度；仅有三张截图不足以替代完整链路证据。

调试日志是辅助诊断证据，正式软件/真实 HIL 接受仍按[交付门禁](../../.agents/rules/delivery_and_coord_gate.md)及[独立 QA 规则](../../.agents/rules/codex_qa_review.md)执行。真实环境发现不符合已接受预期的结果，生成/关联 Issue，交开发 COORD 处理并由独立 QA 复验；缺环境或证据标明阻塞，不签发完整批准。

## 5. COORD 交接建议

PM 保持一个需求及用户验收目标；ARCH 与 ENG-MC、ENG-TH 先核查现有日志/调试 UART，确定启停、记录位置、关联方法、预算、准确路径和分支，补充上述未决条件。需求理解与实施概要按准确版本一并交用户确认，已有有效批准直接引用。调查/方案编制不以实现批准为前置。

确认后由 COORD 查重并关联现有工作，按模块边界登记正式任务：ENG-MC 负责 MC App，ENG-TH 负责 TH App，INTEGRATOR 负责两路日志采集说明和组合联调交接；仅在现有 AP 可观测性不足时派发对应有界 AP 任务。两端同属一个仓库时仍分别冻结路径和共享文件 Owner，遵循现行并发/租约规则。ENG_BOOT_MC、ENG_BOOT_TH 本轮不承担 App 调试实现。

独立 QA 设计正常、相关异常和恢复用例；真实 HIL 操作由授权集成工程师/受控运行器执行并留存物证，独立 Codex 只读审阅同一锁定候选和证据，报告经非作者复核后由 COORD 按范围收件。正式任务 ID、实际会话、候选和运行记录均待有权 COORD 登记，本单不代填。
