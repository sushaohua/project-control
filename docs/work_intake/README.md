# 人工收件入口与填写方法

有助理时，由助理把你的自然语言要求整理成收件单；没有助理时，你按同一个模板填写。两种方式都交给唯一 COORD 读取，使用同一套查重、分类和任务关联流程。

## 三步提交

1. 复制[可填写模板](examples/README_template.md)，先在 `submissions/` 以外的位置填写，保留模板原件。
2. 填好主题和内容后，另存为 `project-control/docs/work_intake/submissions/YYYYMMDD_主题.md`，例如 `20261105_启动问题.md`。使用未占用的新文件名；同名时加后缀。文件直接放在该目录，不放进子目录。
3. COORD 在下次收件检查时读取，返回收件记录。你不用另填三张分类表，也不用维护 Board。

文件进入 `submissions/` 就会成为下一次扫描的输入，因此不要把空模板、填写中的草稿或使用说明放在那里。使用 Markdown 编辑器、Obsidian 或普通文本编辑器均可；填写时不需要 YAML、机器编号或命令行。

## 怎么写

保留 `## 公共约束` 和 `## 指令 1` 这两个标题。每条指令第一行写分类和一句话标题，然后写现象/目标、期望结果及资料。没有的信息可写“未知”或“暂无”，不要求先知道根因。

| 首行分类 | 用于什么 | 首行示例 |
| --- | --- | --- |
| `【问题】` | 已有行为不符合预期，需要调查或修复 | `【问题】部署脚本结束后网关进程退出，根因待查` |
| `【功能】` | 新增或调整一个已经明确的功能 | `【功能】温度面板增加最近十分钟的趋势图` |
| `【需求】` | 产品规则或边界尚未明确，需要澄清 | `【需求】明确重连后是否允许自动继续打印` |

模板默认是 `【问题】`；按实际情况替换首行分类即可。收件器目前按正文关键词初分，COORD 须核对结果是否符合你明确填写的意图；分类不符由 COORD 处理，不要求你反复改写自然语言。

一份文件可以提交多项：复制整段 `## 指令 1` 及其内容，依次改为 `## 指令 2`、`## 指令 3`。每条只写一件独立的事，一条需求后续可以拆成多个角色任务；删除不用的占位内容。代码、日志和命令可作为资料，但不会因写入收件单就被自动执行。

## COORD 怎么处理

COORD 在会话启动/恢复、选取下一批任务前及既有巡检检查点检查该固定入口，使用现有收件器解析和查重，无需助理另行转交。没有持续运行的 COORD/巡检时，保存文件本身不会启动会话；恢复 COORD 后即可继续读取。这里规定入口与检查时机，不表示新增了文件监听或后台服务。

收件顺序：人工 Markdown → 唯一主分类记录（`issues/`、`features/`、`requirements/` 三选一）→ 按既有批准及派单流程关联正式任务 → 更新 Board 投影。用户和助理负责提交原始要求；分类编号、技术拆分、资源安排及正式状态由对应职责处理，不把“已收件”写成“已批准/已开工/已完成”。

COORD 的简短回执应列明：源文件及指令、分类编号、关联正式任务（尚未建立则如实注明）、当前处理阶段和必要待决项。只收件不代表立即占用台架；已有授权按现行规则复用，缺少必要授权或输入时说明具体缺口。

## 收件后的补充与修改

已收件的原文件保留，不直接覆盖、删除或改名。收件器按来源版本和哈希去重，同一文件默认 revision 1，原地修改可能被判为版本冲突。

需要补充、改范围或取消时，新建一份补充单，在“已有关联或批准”中写清原文件名、指令号及已知分类/任务编号，并说明本次变化。COORD 先核对并关联原记录，再按现有版本和在途任务规则处理，避免重复派单；不要求你手写版本 YAML 或替换历史批准。

已有实例：[三项编译与启动问题](submissions/20261105_soc_ap_build_and_startup_issues.md)。
