# C/C++ 编码规范与函数接口设计约束

本规范吸取并继承 `mcu-p3` 主约束总纲（`/home/sushaohua/agents/mcu-p3/AGENTS.md`）及模块化规则体系（`api_modular_design.md`、`c_cpp_coding_standard.md`），作为全工程各子项目（SoC-AP、MCU 固件、协议与驱动）的通用核心编码硬门禁。

所有参与本工程代码编写、架构设计、代码审查与 QA 审计的 AI Agent 及工程师，必须无条件遵从。

---

## 1. 核心指导思想与自研函数硬性门禁

### 1.1 核心指导思想
- **直观性、可读性与确定性永远高于语法技巧和极致性能**。
- **KISS 原则 (Keep It Simple, Stupid)**：严禁编写紧凑、压行、晦涩的“黑魔法”或过度抽象代码。
- **数据流透明**：代码逻辑扁平直白，单步运算与状态变化必须清晰可追踪。

### 1.2 自研函数两大硬性红线门禁 (Strict Gatekeeper)
1. **【硬性门禁 1】严禁编写超过 50 行的自研非结构体函数**：
   - 单个函数长度必须严格控制在 **50 行以内**（不含纯空行与头部注释），只专注做一件事（单一职责原则）。
   - 复杂逻辑必须按处理阶段拆解为带 `static` 修饰的内部小步辅助函数。
2. **【硬性门禁 2】严禁编写超过 4 个入参的自研非结构体函数**：
   - 自研函数参数**严禁超过 4 个**。
   - 若初始化、配置或执行需要传递较多参数，**必须封装为专用的配置/上下文结构体指针**传入（如 `const config_t*` 或 `context_t*`）。

### 1.3 存量继承代码与自研新增模块豁免原则 (Legacy Exemption)
- **自研模块 100% 严格执行**：本工程所有自研新增模块（包括但不限于 SoC 端协议编解码、流式解析器、状态机分发、驱动适配与自研中间件），必须 100% 遵守上述函数规模（$\le 50$ 行）、入参限制（$\le 4$ 个）及防御性空指针校验。
- **外部存量与冻结接口豁免原则**：
  - 针对继承自开源社区或三方库的存量代码（如 Marlin 运动控制代码、第三方协议栈），以**最小修改预算 (Minimal Diff Budget)** 优先，严禁大范围无关重构或修改已有外部签名。
  - 对于已由上游规范协议正式冻结的跨模块 ABI 公共入口（如固定 5 参数的历史 C 兼容入口），公共包装入口在必须兼容外部调用的同时，其实际实现必须立即委托给符合入参 $\le 4$ 且长度 $\le 50$ 行的静态辅助函数处理。

### 1.4 Linux 用户态第三方中间件 C++ 适配层豁免原则 (Middleware Wrapper Exemption)
- 针对 SoC-AP Linux 用户态对外封装 Fast DDS、D-Bus 等外部 C++ 中间件库的 SDK 适配层（如 `aisoc_dds`、`aisoc_dbus`）：
  - **允许最小必要使用外部 C++ 库实体**：允许按第三方库官方 API 规范进行必要实例化与异常捕获（`try-catch`），豁免 `-fno-exceptions` 编译门禁；
  - **自研层有界硬性配额约束**：自研适配层必须通过严格的原子 CAS 配额机制（如 `AISOC_DDS_MAX_PARTICIPANTS`、`MAX_PUBLISHERS`、`MAX_SUBSCRIBERS`）对实体总量设定硬性上限，并在创建失败时原子回滚，从架构上 100% 杜绝无界泄漏；
  - **函数规模硬门禁照常执行**：所有自研封装及辅助函数依然 100% 严格执行行数 $\le 50$ 行、入参 $\le 4$ 个、首行防御性空指针校验等门禁要求。

## 2. 函数接口设计与防御性规范

### 2.1 入参在前、出参在后，只读入参必加 `const`
- 函数参数严格遵循调用顺序：入参在前，出参在后：
  ```c
  Status module_process(const InType* in_data, size_t len, OutType* out_result);
  ```
- 所有只读指针必须显式声明为 `const Type*`，防止内部误修改。

### 2.2 函数入口防御性空指针检查 (Guard Clause)
- 所有接收指针参数的对外公开函数，首行必须对指针进行非空检查，指针非法必须立即返回错误码：
  ```c
  if (in_data == nullptr || out_result == nullptr) {
      return Status::ERR_INVALID_ARGUMENT;
  }
  ```

### 2.3 返回值统一度量，数据出参化
- 易发生异常或失败的函数，返回值统一固定为“状态结果”（强类型枚举错误码 `Status` 或 `bool`），业务数据统一通过末尾的输出参数指针传出。

### 2.4 头文件 (.h) 职责与防重入保护
- **标准头文件卫士 (Header Guard)**：头文件必须包含标准的防重入保护（`#ifndef` / `#define`）或 `#pragma once`，且提供 C++ 兼容守卫（`#ifdef __cplusplus extern "C"`）。
- **头文件只声明、绝不定义实体变量**：严禁在 `.h` 中定义全局变量；跨文件共享变量必须在 `.h` 中加 `extern` 声明，实际定义落在对应的 `.c/.cpp` 中。
- **包含最小化与源文件自包含校验**：`.h` 只包含公开接口声明所需的最少头文件；源文件第一个 `#include` 必须是自身对应的 `.h` 头文件。
- **内部函数与私有变量强制 `static` 修饰**：未暴露给外部调用的辅助函数、内部状态变量，必须加 `static` 修饰，限制在编译单元内部。

## 3. C/C++ 语言规范与底层内存安全

### 3.1 指针显式化，禁用指针黑魔法
- **严禁压缩指针运算**：禁止编写 `*dst++ = *src++;` 这类自增解引用合并写法，统一改用数组下标 `dst[i] = src[i];` 或显式分步拆行递增：
  ```c
  /* 正确示例：显式分步 */
  *dst = *src;
  dst++;
  src++;
  ```
- **指针深度限制**：严禁使用超过二级的多重指针（禁止出现 `***ptr`）。
- **运算拆行**：指针解引用与取地址操作必须独立成行，禁止把 `*p`、`&x` 混入复杂的组合算式中。

### 3.2 控制流扁平化
- **禁用嵌套三元运算符**：条件选择统一使用完整展开的 `if - else if - else` 代码块。
- **卫语句优先 (Guard Clause)**：函数内大括号嵌套层级**严禁超过 3 层**，优先使用提前 `return` 或 `break` 消除深层缩进。
- **显式拆解复合条件**：超过 2 个逻辑判断（`&&` / `||`）时，必须拆解为具有具名含义的临时布尔变量。

### 3.3 命名与数据类型约束
- **严禁单字母命名**：变量名统一采用语义清晰的蛇形命名法（`snake_case`）。除 `for` 循环索引允许使用 `i`, `j` 外，严禁使用单字母或无意义缩写。
- **固定位宽类型优先**：源文件必须包含 `<stdint.h>` 与 `<stdbool.h>`（或 C++ `<cstdint>`），统一使用 `uint8_t`、`uint16_t`、`uint32_t`、`int32_t`、`bool` 等位宽明确的类型，杜绝跨平台隐式溢出。

### 3.4 现代 C++ 裸机轻量化规范 (C with Classes)
本节严格约束 MCU 裸机固件以及 SoC-AP 核心通信协议序列化与状态机纯自研模块（Linux 用户态第三方中间件 SDK 适配层按第 1.4 节执行豁免）。若模块引入 C++（编译选项 `-fno-exceptions -fno-rtti`），必须严格遵循：
- **零动态堆内存 (Zero Dynamic Allocation)**：严禁使用 `new`、`delete`、`malloc`、`free` 以及依赖堆的 STL 容器（如 `std::vector`、`std::string`），统一使用定长静态数组、有界视图或栈对象。
- **禁用异常体系与 RTTI**：禁止使用 `throw`、`try`、`catch` 与 `dynamic_cast`、`typeid`。
- **显式两阶段初始化**：严禁在全局对象构造函数中操作底层硬件或分配资源，构造函数保持平凡或空实现，统一调用显式的 `init()` 方法。
- **单参数构造显式标注**：单参数构造函数必须显式声明为 `explicit`。
- **编译期静态校验**：通信协议帧、硬件寄存器对齐结构体必须使用 `static_assert(sizeof(...) == EXPECTED, "...")` 校验。

## 4. 嵌入式外设与底层硬件操作约束

### 4.1 寄存器访问与“读-改-写”分步执行
- **拒绝硬编码数值与裸魔数**：严禁直接写入十六进制裸常数，位操作统一使用显式移位（如 `(1U << 5)`）或标准库位掩码宏。
- **分步执行修改**：严禁在单行内合并清除与置位操作。修改寄存器位时必须严格分为两步（Clear 后 Set）。
- **硬件指针强制修饰**：直接访问硬件寄存器的指针必须显式声明为 `volatile`。

### 4.2 轮询与等待超时保护 (强制门禁)
- **禁止空循环分号死等**：严禁编写类似 `while (!(UART->sts & FLAG));` 的无防护硬件轮询死循环。
- **强制展开大括号并带超时计数器**：所有状态轮询与硬件标志位等待必须展开大括号，并加入超时计数器退出分支，超时返回明确错误码。

### 4.3 外设初始化分段标注
外设驱动初始化必须按硬件时序分步实现并加以注释标注：
- `/* 步骤 1: 使能外设时钟 */`
- `/* 步骤 2: 配置 GPIO 引脚复用与上下拉 */`
- `/* 步骤 3: 配置控制器核心工作参数 */`
- `/* 步骤 4: 使能外设模块 */`

## 5. QA 独立审查与验证核查点

在代码审查阶段，审阅者（QA）必须将本规范列为前置阻塞门禁（P0）：
1. 核查新增自研函数行数：无任何函数超过 50 行（若超标立即驳回要求拆解）；
2. 核查新增自研函数参数：无任何非结构体自研函数参数超过 4 个（若超标立即驳回要求封装结构体）；
3. 核查内存安全性：无动态堆内存分配、无指针黑魔法、指针深度 $\le 2$；
4. 核查控制流：无超过 3 层的深层嵌套，入口具备防御性空指针校验。
5. 对适用的 SoC-AP 任务，按第 6 节核查资源预算、实测结果、依赖清单、裁剪依据及必要的功能和故障验证；未执行或目标环境未知的项目须明确记录，不以主机结果代替目标板验证。

## 6. SoC-AP 资源、代码与发布包最小化

本节适用于 SoC-AP 自研业务模块、服务以及其构建和部署制品。在满足已批准功能、安全、可靠性、可维护性和通信契约的前提下，设计和实现应优先降低内存、存储和代码规模。第三方及继承代码继续遵守第 1.3 节的最小修改原则；第 1.4 节的适配层例外保持适用。

### 6.1 最小化内存占用

- 按实际需求设置缓冲区、队列、缓存和并发数量的上限，禁止无界增长；避免不必要的数据副本、常驻缓存及重复维护状态。
- 根据实际数据范围选择类型并管理对象生命周期，不为未批准或可能用不到的功能长期预留资源；不得以缩小类型造成溢出或破坏协议兼容。
- 任务适用时记录空闲、正常工作和峰值负载的内存占用、测量方法及环境，并与已批准的资源预算比较。

### 6.2 最小化存储占用

- 避免重复存储可重建的数据，保留必要配置、诊断信息和恢复能力。
- 为日志、缓存、临时文件和持久化数据设置容量上限或保留期限，明确空间耗尽时的处理方式。
- 记录发布包大小、安装后占用和运行期数据增长；目标板可用空间或预算未知时明确标记待确认，不虚构阈值。

### 6.3 最小化代码生成

- 优先复用项目内已接受的模块、公共接口和第三方依赖，避免重复实现；只实现已批准需求所需的代码，不生成无用途的模块、空壳服务、重复封装或扩展点。
- 必须使用自动生成代码时，限制生成范围，记录生成工具、版本、输入和生成方法，避免手工复制多份生成结果。
- 保持代码清晰、可审查和可测试；不得为减少行数压缩代码，也不得删除必要的参数校验、错误处理、日志或安全保护。

### 6.4 发布包与依赖库最小化

- 发布包仅包含已批准功能在目标环境运行必需的程序、共享库、配置和资源；不将开发工具链、头文件、示例、测试、文档或未使用的库直接打包进生产镜像。
- 引入或更新依赖时，记录直接及传递依赖的版本、来源、许可证和用途；优先复用目标平台已接受且版本兼容的库，避免重复打包同一库的多个版本或功能相同的库。
- 按实际功能裁剪可选组件、插件、协议和资源；可评估编译器和链接器体积优化、未使用代码剔除及符号裁剪，但须满足工具链兼容、调试和故障定位要求。
- 分别评估动态链接和静态链接对发布包、运行内存和维护的影响，依据实测和平台约束选择，不预设某一种必然更小。
- 对发布候选记录依赖清单、各库大小、发布包总大小、目标环境实际占用及相对基线的变化；移除不必要依赖，对必要但体积较大的依赖说明原因。
- 裁剪后验证程序启动、已批准功能、动态库加载、插件发现、错误处理及必要故障诊断；不得因减小体积破坏功能、安全、版本兼容或许可证要求。
- VMware 和目标 SoC 的依赖分别核对；目标 sysroot、BSP 或库版本未知时记录待核实，不把主机依赖当作目标板可用证据。

### 6.5 预算、验证与例外

- 任务卡按适用范围列出资源预算、负载、测量方法和验收条件。预算尚未确定时先记录实测基线及增长原因，不虚构数值。
- 新增依赖、明显增加资源占用或确需重复实现时，作者说明原因、影响和替代方案，由相应 Owner 审查。独立 QA 按任务范围核查证据；目标平台未具备时记录缺项及后续验证条件。
- 最小化不得降低安全、功能、可靠性或既有硬性编码门禁；有关性能、内存与存储的取舍须记录依据。
