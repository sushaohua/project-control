## 填写结构与阶段门禁

本模板版本适用于新建卡和本轮需要修订的活动卡。旧卡/旧签署不批量改名；按准确 revision 补充变化与适用范围。`template_version` 是模板版本，不表示检查器已经实现该版本 schema。

`dependency_conditions` 每个对象包含以下字段，`task` 必须对应 `depends_on`；父任务的相关能力门要在这里显式落实，不能用“父任务存在”或“前置 Done”代替。外部输入无内部 task 时，在 `read_sources`、`inherited_gates` 和前置表记录提供者、版本、接受证据与恢复条件，不编造内部 ID。

```yaml
dependency_condition_fields:
  task: null
  required: null
  accepted_version: null
  acceptance_evidence: null
  acceptance_report_sha256: null
reviewer_session_fields:
  role: null
  platform: null # QA 或 QA 作者的独立 ARCH 复核填 codex
  model: gpt-6-luna # AI Reviewer计划模型；HUMAN填null；实际模型记审查报告
  actual_model: null # 审查完成后按报告回填
  planned_session_alias: null
  session: null
  reviewed_task_revision: null
  artifact_version: null
  decision: null # 新签署使用 APPROVED / REJECTED；未审保持 null
  evidence: null
  report_sha256: null
model_override_fields:
  role: null
  session: null
  requested_model: null
  actual_model: null
  reason: null
  coord_approval_evidence: null
```

上面三个 `*_fields` 仅说明对象结构，不是可原样粘贴的有效前置/Reviewer/模型例外；按实际任务实例化到数组。SHA256 的对象域必须明确（候选清单、源码文件、制品或报告），不能混用。报告自身哈希在报告写完后由交接记录/卡片保存，不要求报告把自己的哈希嵌入自身。

| 阶段 | 本卡需要满足的条件 | 不可替代的证据 |
| --- | --- | --- |
| Backlog → Ready | 实际输入、父任务相关能力、路径、授权、检查安排、资源、有限预算与期限齐全；blocked=false | 准确消费版本和接受依据；不要求尚未产生的本票候选或签署 |
| Ready → InProgress | 作者回执，实际会话/工作区/任务revision/有效租约一致 | 实际认领记录；计划会话名不算执行者 |
| InProgress → Review | 提交候选或文档版本、差异、原始命令结果、未执行项 | 同一候选的完整交付；不能只提交exit 0 |
| Review → Verify | 每项必需独立评审接受准确候选；作者不得占本产物独立评审位 | 实际session、任务revision、候选版本、报告及其SHA256 |
| Verify → Done | 本票正常/异常判据完成，适用的独立运行/集成和收件证据齐全 | COORD记录接受范围、版本和依据；CLI或文档APPROVED不自动改状态 |
| 证据撤回/输入变化 | 保存旧报告，追加失效范围、受影响消费者、替代票与恢复条件 | COORD据证据修当前适用关系；Blocked不是新status |

这些是人工必须核对的条件。现有 `check_task_graph.py` 仍有任务类型/阶段覆盖限制；结构检查绿灯不能代替本表，尚未实现的检查不得写成自动门禁已生效。

本模板是通用任务字段约定，不等于现有工具写死的离线V2 schema。V2票还需按实际任务补专用适配字段（如readiness_pending、聚焦case组与证据目录）；若工具旧约束与真实任务冲突，登记工具缺口，不填造待办、版本或结果换绿灯。

跨节点任务将“契约接受 → 各节点必要实现 → 工程联合调试 → 独立组合验收”显式关联。`coordination` 是协作目录，实际前置仍写 `depends_on/dependency_conditions`；最终验收票不能反过来作为单板实现开工前置。单板微步只验本票交付；最终组合需锁定 AP、MC、TH 中实际参与的全部版本和所需固件，不要求每张单板票重复产出所有节点制品。

验收层级按[交付门禁 §4.2](../delivery_and_coord_gate.md#42-软件与真实hil双门禁及批准范围2026-11-02)登记在既有 `verification_scope`、`verification_environment` 和 `required_evidence_level` 中：模块软件、跨仓软件链路、最终硬件功能分别说明。硬件功能最终验收使用 `hardware-verified`；ARCH 定义链路、权威字节契约和真实效果，COORD 用既有 `coordination.acceptance_task` 关联组合验收卡并安排资源，不把最终 HIL 设为所有上游卡开工前置。

在 `resources`、验证用例和正文中列实际参与节点/固件、各串口角色与速率、台架窗口/授权、受控 HIL 执行器及采集/收件入口；用同一请求或采样关联入口结果、业务原始帧、Debug 与测量/物理效果。缺环境或执行器登记对应阻塞，不能以 PTY/模拟库或本地状态替代；前置软件范围的接受继续有效，不批量改写历史 Done。

## 目标

一个明确用户行为或工程结果，例如“本版 Marlin 温度回复分三次到达后完整解析，并只发布一次对应结果”。

## 非目标与不可修改项

列出相邻模块、公共协议、真实设备操作和产品范围。允许写入的源码、配置、构建输出与任务证据都要映射实际位置；角色表中的建议目录不等于授权。

## 前置交付与 Ready 条件

| 生产卡/外部来源 | 产物 | 准确版本 | 本卡怎样用 | 何时可用/缺口处理 |
| --- | --- | --- | --- | --- |
| 待按任务填写 | 不写“看上文” | 原件路径与 commit/版本/哈希 | 说明依赖理由 | 明确能力/接受条件；缺项登记提供者与恢复条件 |

调查/设计可以核查未知，但不能编造输入；实现只能使用本轮相关已接受的接口、样例与工程。否定调查 Done 不满足依赖该能力的实现。外部条件、资源冲突、阶段策略分别说明，不统统伪装成技术前置。

Ready 前明确五项、实际检查/收件安排、准确写路径、资源、预算与检查点。构建/运行卡明确命令，文档卡明确核对方法。候选代码、运行日志等是完成后交付，不要求开工前已经存在。

## 谁做和谁检查

按[公共规则§4.3的任务类型矩阵](../04_公共看板与读写协议.md#43-按任务类型安排检查)落实必需岗位。reviewer空数组、verifier/integrator空值只是Backlog占位，不表示这些环节统一免检；派单前按类型补齐，确实不适用时写理由与接受依据。

所有 AI 角色的默认模型为 `gpt-6-luna`。独立 QA 平台统一为 Codex，QA、QA Verifier及QA作者产物的独立ARCH复核都使用该模型，规则见 [Codex QA 规则](../codex_qa_review.md)。Reviewer 为 QA 或承担 QA 作者产物 ARCH 复核时，在对应条目补 `platform: codex`、`model: gpt-6-luna` 和 `planned_session_alias`；实际 `session` 与实际模型由 COORD 落实后登记。其他 Reviewer/Integrator/HUMAN 的岗位与批准要求保留。偏离默认模型必须先在 `model_policy.approved_overrides` 记录角色、会话、请求/实际模型、原因和COORD批准证据。

按本卡写作者、必需 Reviewer、额外运行验证、合入/装配、收件/状态登记五个环节；不适用项写原因。QA 作者的用例、预期和工具由独立 ARCH 检查；`streamlined-v1` 不递归检查独立 QA 报告；多人 Reviewer 按角色逐项映射实际入口。具体规则见 [[AI_SoC_协作方案/04_公共看板与读写协议#4.3 按任务类型安排检查]]。

## 验收

先固定独立预期。帧级CRC正确、命令语义正确、请求关联成功、真实物理闭环分别验证；旧帧、错源/目的/命令/序号、请求回显、错误长度和零响应不得被一般帧解码成功替代。正常场景零有效关联响应必须失败；失联/坏包等负例按其冻结预期判断，不能一律要求有响应。

给出可运行的命令／步骤、可观察预期、必须覆盖的相关正常和故障场景、所需证据层级，以及谁对哪个版本检查。调查任务写怎样检查来源和结论；离线 Mock 不以真实打印或物理温度作为通过证据；HIL 查询需指定 MCU 原始报文，真实动作和目标 SoC 验收分别声明。

## 交付

候选 commit／PR（适用时）、准确改动路径、实际检查记录与制品哈希、已做/未做、未解决项、回退方法。向 `handoff` 登记的实际 COORD 入口交结果，说明证据位置并取得收件确认；独立对话需要人工转交时明确写出。只有 COORD 在所需验收与合入条件满足后才能设 Done。

接单前给五项简短回执，缺必要内容先登记缺口；接单不自行更新正式状态。任务中途变更依据准确 revision 通知，不能把旧输入的测试沿用为新输入通过。

调查/设计任务的 `requirement`、`feature`、`icd_versions` 可填 `null`/`[]` 并说明要产出什么，不能被尚不存在的接口挡住调查。实现/集成任务必须补齐本轮相关已接受输入。文档任务用 document/source-reviewed 证据和文档 Reviewer；主机试验用 host＋experimental；真实设备任务另列设备、固件及 hardware-verified 证据。示例值不能直接冒充已落实的角色或已通过基线。


## 当前细任务与工作包

任务和顺序见 [[AI_SoC_协作方案/03_实施步骤与首个闭环]]；TASK 工作包不直接派单。任务实时状态只见卡与证据，模板不重复“全部未认领”等快照。

岗位名不是实际执行者。`owner` 与 `executor.agent_id` 相同；Reviewer 逐项记录岗位/实际会话/版本/结论；接收方按 `handoff` 登记。空字段表示待补，不代表服务存在。

输入升级、旧证据适用范围与误判撤回按 [[AI_SoC_协作方案/04_公共看板与读写协议#4.4 完成后变更与证据撤回]]。已接受的旧版完成事实保留，新版另建修订/复验；不能把旧通过贴到新候选。

登记VM与SoC共用源码/契约/进程/生命周期、平台差异及本阶段证据。VM能力卡须测试实际IPC与真实模块界面，不将离线原型作系统完成；SoC迁移卡明确BSP/sysroot/显示驱动输入和实板出口。历史Done只按原对象复用；生成绑定由契约源生成。未来命令标planned-not-runnable，Ready前替换为实际入口，不能执行占位内容。


## 连续调度与服务器沙箱QA（2026-10-29）

COORD按总控执行清单拉起作者/检查者并核对每票闭环。Reviewer条目补充`session_evidence: {path: null, sha256: null}`，绑定真实会话来源导出；`reviewed_task_revision`、`evidence`、`report_sha256`必须对应准确对象。仅 legacy 的 QA 条目须填写 `report_review`，其结构同独立 Reviewer 条目（role: ARCH），绑定 QA 报告的独立非作者复核；`streamlined-v1` 不默认生成该字段。

报告结构、`server_qa`及内容门禁见[QA模板](QA审查报告模板.md)。实际模型不暴露则记unknown及限制，不把请求值充作已核实实际模型。Ready阶段只需落实实际安排及环境能力，不要求尚未产出的QA结论；收件阶段这些证据必须实际具备。

## 正常流程E2E与Issue补充（2026-11-02）

适用验收按[交付门禁§4.1～4.3](../delivery_and_coord_gate.md#41-正常流程优先与正负成对验收2026-11-02)及[E2E与Issue规则](../e2e_issue_verification_flow.md)执行。沿用现有任务类型、状态和主模板；下列为适用任务的附加人工核对字段，旧卡不批量迁移，不表示检查器已支持这些字段。

涉及跨服务触发的设计/实现/集成卡，Ready前在ICD中接受以下契约并引用准确版本；本卡若负责产出契约，开工时可标待设计，交付前接受。纯文档调查等不适用项写理由。QA与COORD须核实触发已实际实现，不能只查字段存在。

功能验收先测正常用户操作，再测故障与恢复，安全前检始终先行。正常条件下超时仍UNKNOWN/无响应属于失败；缺硬件是阻塞，负例通过不抵扣正例缺失。按语义核对界面反馈、下一步、关键导航及持久化。必测清单逐项有实际证据，软件通过不能自动满足真实HIL；文档审查不强要硬件。

修复票关联Issue、准确失败候选、复现步骤、预期和证据，明确原case与受影响回归。新候选经独立复验、所用策略的必需接受和COORD收件后关闭；在途缺陷优先原卡退修，历史Done缺陷另建关联修复/复验，保留旧证据及累计返工次数。
