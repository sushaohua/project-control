## 当前独立 QA 执行方式

依据用户 2026-10-26 的明确要求，所有未完成及新建任务的独立 QA 审查、QA Verifier 与 QA 作者产物的 ARCH 复核，统一使用独立 Codex 会话，默认模型为 `gpt-6-luna`。执行与登记以 [Codex QA 规则](codex_qa_review.md) 为准；本条更新执行平台和默认模型，不改变岗位分工、必需批准者或历史签署。待启动的计划别名不能当成实际会话，也不表示自动调度已部署。

## 1. 当前放在哪里、怎样运行

当前任务原件在本目录 `tasks/`，由唯一 COORD 写正式状态；[[AI_SoC_协作方案/看板]] 是带更新时间的人工投影。Git 记录修改历史，Obsidian 用来阅读和编辑。没有自动认领、监听、续租或唤醒服务。

正式开发时可将管理资料迁到 Linux 的独立 `project-control` 仓，代码使用隔离工作区；迁移前后记录唯一原件和切换版本。可执行契约随 `soc-ap` 代码维护。目录树、代码白名单须映射真实工程，不因文档有路径就存在授权。

### 1.1 本轮先选择一种交接方式

| 方式 | 谁发送、谁接收 | 一轮结束后 |
| --- | --- | --- |
| 独立会话、人工转交 | 作者保存证据并交位置；用户通知原 COORD 读取 | 用户向原 COORD 发继续/读取消息 |
| 主对话本轮委派子 Agent | 已明确委派后，作者通过工具反馈并保存证据，主 COORD 收取 | 本轮结束后仍需用户继续；不自动常驻 |

首次按 [[AI_SoC_协作方案/07_第一次启动与日常使用#1.1 指定唯一 COORD 并登记执行方式|统一启动指令]] 登记实际 COORD 与反馈方式。岗位表不代表团队已经运行；把一段回复分成多个角色标题不等于独立 Agent。

## 2. 看板展示什么

只展示任务、实际负责人、当前阶段、证据、卡点和下一步，以及三个阶段出口。明细以任务卡为准；看板标 `projection_updated`。两者不一致时先核对卡和证据，再由 COORD 修投影，不能用旧手册覆盖新状态。

工作包 `TASK-*` 不直接派单，`planning_relations` 只是范围关联。MS/PL 细卡的 `depends_on` 才是直接前置；每条依赖还须符合卡内“产物与使用条件”。一张细卡只有一个 `primary_work_package`，其他关联不重复计算完成数量。

## 3. 读写和记录位置

| 对象 | 权威写入者 | 其他执行者怎样交接 |
| --- | --- | --- |
| 产品范围/需求 | PM 整理，HUMAN 确定范围 | 提候选/变更，不自行增加产品功能 |
| 架构/接口/错误码/schema | ARCH，受影响模块与 QA 按范围评审 | 提 RFC；批准后由任务内作者修改准确路径 |
| 模块代码/测试 | 任务白名单内作者 | 跨模块问题发依赖请求，不越界顺手修 |
| 独立样例/预期/验收报告 | QA，定义与报告由独立 Reviewer 检查 | 不用实现输出倒推唯一答案 |
| 任务 owner/status/revision/占用及看板 | 唯一实际 COORD | 提实际结果；作者不能自行宣布 Done |
| 评审/运行原始证据 | 对应实际执行者写自己的独立位置 | 更正另留记录；COORD 引用原件，不代写原始通过结论 |
| 合入、候选清单、构建装配 | INTEGRATOR | 模块提交候选；冲突修复交相关作者 |

人工模式不强制先创建 JSON 事件系统。派单时，`handoff.evidence_location` 写实际授权的报告/日志位置；`handoff.transport` 写“人工转交”或“本轮主子反馈”；COORD 的收到/补材料回执保存在明确的任务交接记录并由 `acknowledgement` 引用。收到、评审通过、合入、Done 是不同结果。

不得把密码、私钥放进公共卡或日志；访问凭据按已有安全方式提供。资源和源码权限来自用户有效授权，岗位或任务状态不能扩大权限。

## 4. 状态与转换规则

生命周期保持 `Backlog → Ready → InProgress → Review → Verify → Done`；阻塞另记 `blocked`、原因、提供人和恢复条件。

| 转换 | 当前人工模式的检查 | 谁写入 |
| --- | --- | --- |
| Backlog → Ready | 五项、相关输入使用条件、检查者、资源/预算/检查点齐全；不要求尚待产出的结果 | COORD |
| Ready → InProgress | 执行者回执；实际身份、准确 revision 与有效占用登记一致 | COORD |
| InProgress → Review | 交付准确文件/代码版本、实际证据、已做/未做和缺口；代码才要求候选 diff/commit | COORD |
| Review → Verify | 所有必需评审者对同一版本给结论；调查/文档用文件版本，不强要镜像 | COORD |
| Verify → Done | 本类型证据齐全；代码核对集成版本及受影响检查，文档核对对应评审与原件 | COORD |
| Review/Verify → InProgress | 修复原因、受影响证据和新任务 revision 记清；旧记录保留 | COORD |

Verify 是“核对本卡完成条件”的阶段，不一定再启动一名 QA。普通文档无需编造构建或运行结果。状态只说明对应任务范围，不自动宣布工作包、双端或产品完成。

### 4.1 派单前必须明确的五项

| 项目     | 具体内容                               | 谁准备、缺了怎么办                             |
| ------ | ---------------------------------- | ------------------------------------- |
| 自己的任务  | ID/revision、一个结果、非目标、岗位；开工前登记实际执行者 | PM/ARCH 明确范围，COORD 派单；目标混杂先拆          |
| 输入版本   | 每项来源/前置卡、产物、准确版本、用途、使用条件；引用接受记录    | ARCH/模块/INTEGRATOR 核对；调查可核查未知，实现不能猜接口 |
| 允许修改范围 | 真实仓库/工作区、文件白名单、禁止项、证据输出、设备/命令范围    | COORD 在已有授权内落实；共享文件由 Owner 协调         |
| 完成标准   | 正常与相关故障的预期、步骤、证据层级、检查者及独立性         | QA/相关 Reviewer 核对；只有“测试通过”不够          |
| 向谁交结果  | 实际 COORD 入口、反馈方式、证据位置、回执与后续检查安排    | COORD 登记；没有服务就采用实际人工/主子渠道             |

调查/设计可从问题与来源开始，不要求先取得它要产出的最终接口。实现/集成必须有本轮相关已接受输入；验证必须知道检查哪个候选和哪个预期。未知、否定或过期输入不满足依赖该能力的实现。

### 4.1.1 岗位名称与实际执行者分开记录

| 字段 | 含义 |
| --- | --- |
| `proposed_owner`、`executor.role` | 建议岗位、本轮岗位，不代表有人在运行 |
| `owner`、`executor.agent_id` | 同一个实际执行者入口；未认领为 null；`run_id` 追踪本次执行 |
| `reviewer` | 必需评审岗位数组，默认逐项通过；不是任选一个 |
| `review_assignments.reviewer_sessions` | 每项明确 `role/session/decision/artifact_version/evidence`；session 等空值未分配，不是通过 |
| `verifier`、`verifier_session` | 额外独立运行检查岗位/实际入口；不适用为 null，并在卡中说明 |
| `integrator`、`integrator_session` | 本卡代码合入/候选装配岗位和实际执行者；无此动作时 null |
| `handoff` | 实际接收方、渠道、证据位置和收件回执引用 |
| 看板 `owner: COORD`、`coord_session` | 文档岗位与实际协调会话，不能混用 |

实际工具没有 ID 时记可定位的对话名/入口，不编造标识。作者与该产物的独立检查者分开；多人评审不得由作者换岗位名凑齐。同一名非作者可按登记承担多项检查职责，但每项结论仍单独对应版本。需更换必需评审安排时由相关 Owner 确认、COORD 修订卡，不能悄悄跳过。

### 4.2 接单、占用和交付

1. COORD 准备卡与实际反馈入口，作者按五项返回简短回执；缺必要输入先记录问题。
2. 开工前 COORD 登记 `lease` 的 `owner/task_revision/lease_id/expires_at`，以及 `checkpoint` 和实际资源。它是人工占用记录，不是工具锁。期限由本任务投入和运行安排决定，不用固定时长假装适合所有任务。
3. 到检查点或期限前，作者交进展；COORD 核对后明确续领并记录新期限。没有收到续领，过期后停止新增修改/设备操作，保留检查点。COORD 本轮结束不能假设仍会自动续租。
4. 作者保存自己的证据，按登记渠道提交任务/revision、实际版本、产物、检查、缺口和下一步；COORD 明确“已收到”或“需补材料”。
5. COORD 组织对应评审/验证/合入，再更新状态和看板投影。到预算/重试界限时报告已完成与缺口，不无限空转。

重派前确认旧执行者和运行进程已停止或隔离，保留旧工作区；真实设备不能只靠一条过期记录交接。独立对话由用户转交通知；主子模式只在本轮通过实际工具反馈。

### 4.3 按任务类型安排检查

| 类型/例子 | 作者交付 | 独立检查 | Verify 如何结束 |
| --- | --- | --- | --- |
| 文档调查 MS-01 | 工程登记、原件与未知项 | ARCH 检查来源/准确文件版 | 接受登记；MS-02 的复现另做，不在这里冒充 |
| 源码调查 MS-03/12 | 代码入口、配置、能力与缺口 | FWD/SIM/QA 对需用部分逐项核对 | 结论可否定；下游另看使用条件 |
| 运行调查 MS-04 | 准确端点和实收日志 | ARCH 评审，QA 核对实际运行结果 | 双向收发证据符合本卡；桥接修复另派 |
| QA 作者 MS-02/06/11/17/19/22 | 构建/测试执行或预期设计及报告 | 独立 Reviewer 检查方法、来源与准确版本 | 不机械再加第二层 QA；作者不能独自批准报告 |
| 代码实现 MS-07 等 | 候选代码、模块检查、原始日志 | Reviewer＋独立 QA，INTEGRATOR 合入 | 集成 SHA/组合及受影响用例符合要求 |
| 集成 MS-18/20/21 | 构建入口或准确候选清单/制品 | ARCH 评审、独立 QA 检查本卡构建/启动标准 | 不提前要求最终端到端卡通过，防止循环 |
| 产品设计 PL-01/02 | 范围/设计/细卡与未决项 | 卡内必需 Reviewer；范围由 HUMAN 决定 | 接受范围/设计不等于软件实现或未知事实已证实 |

文档用 document/source-reviewed；构建、主机模拟、硬件按实际要求分别留证据。证据层级不能代替具体场景。QA 不为通过验收偷改实现，修复回原作者；独立上下文也不能代替原始来源与可复核结果。

### 4.4 完成后变更与证据撤回

1. ARCH/相关 Owner 登记变更原因、旧/新输入版本和影响到的生产者、消费者、模拟器、样例、测试及候选。
2. 正常旧版 Done 保留，只对旧版本有效；给新版本建小型修订/复验卡。若旧结果本来误判，追加撤回原因/证据，不删除原始记录。
3. COORD 记录失效的适用关系、受影响下游及恢复条件；正在执行的相关部分先保存检查点，不能把旧预期套到新接口。
4. INTEGRATOR 提供新候选组合，QA 检查受影响范围，必要时检查未改部分的关键回归；接受后下游使用新组合。

因此“前置 Done”只是条件之一；每次派单仍核对产物版本、能力结论与接受记录。接口变更不要求无限级联重写全部模块，但也不能遗漏真正消费者。

## 5. 什么时候读取

接单时读入口/B0、本岗位、本卡与相关输入；开工前核对 revision、人工占用、白名单和资源；发生变更时读影响与准确新版本；交付前核对范围和证据；会话恢复时从卡与证据重建。无需每次读整库，也不依赖旧对话记忆。

没有通知服务时采用任务交接与用户继续消息，不要求已结束的 Agent 后台轮询。文件保存成功不等于接收方读到。

## 6. 未来自动化接口（尚未部署）

只有另行开发、部署并验证后，才可采用以下结构；不作为当前调查的开工门槛。

```text
project-control/
  tasks/                    COORD 唯一写权威状态
  events/<agent_id>/         作者在自己目录创建不可变事件
  inbox/<agent_id>/          COORD 分发任务或回复
  reviews/                  原始评审证据索引
  resources/                占用/租约记录
  artifacts/                制品与日志索引
  views/board.md            从任务生成的只读视图
```

事件同时记录实际 `actor_agent_id`、岗位 `actor_role`、run_id、task_id/revision、lease_id、输入版本、候选及证据。作者在自己的 **events** 目录创建临时文件，再同文件系统原子改名为唯一事件；不写 COORD 的 inbox。接收服务校验身份/版本/租约、去重、持久化后给 ACK；ACK 不等于验收通过。

跨主机需要实际控制 API/收件服务，Git 同步和文件 rename 不能实现分布式认领。自动化再实现事务、过期写入拒绝、资源隔离与故意违规的拦截测试；在完成前只能称人工检查，不能称权限由系统保证。

## 7. 并行与资源

起步通常一张卡执行，最多两张实现卡并行；作者每次只承担一项活跃实现。评审按资源先后安排，不要求所有岗位常驻。

当前只读级联恢复按[2026-10-28 任务重排](../../docs/planning/workflow_replan_20261028.md)执行：契约和必要输入接受后，AP、MC、TH 可在独立范围内开发，不将最终 MS-11 HIL 通过反向设为 TH 实现开工条件。最多两张实现卡并行，共仓共享文件和物理台架串行；MC-only 与双 MCU 的最终证据分别验收。原 MS 卡较广范围及未覆盖门禁继续保留，不能用有限只读恢复关闭全部原范围。

不同 worktree 隔离修改，合入同一共享逻辑仍需协调。FWD 的共享解析路径、SIM 的实例端口/输出目录、构建输出和真实设备分别登记资源；不得靠不同任务名重复占用。通用构建/合入由 INTEGRATOR，公共契约由 ARCH 与受影响 Owner 协调。同一集成分支的冲突修改、共享契约合入和 rootfs 装配串行。板卡、UART、烧录器分别登记资源占用/租约，任务占用不自动授予设备使用权。

## 8. 失败与停止

缺输入先留证据并发依赖请求，继续本卡不受影响的部分；越界改动先安排准确任务。达到预算、检查点或重试界限时停下重复尝试，报告选择，不靠新建卡绕过限制。检查通过即结束本卡，不无期限“优化”。

生产固件/硬件范围、新产品取舍和授权外操作仍由实际负责人决定；例行已授权工作无需反复询问。失败预案见 [[AI_SoC_协作方案/12_项目风险清单与失败预案]]。

## 9. 哪些控制真的存在

分别记录“规则已写、人工已执行、工具已部署、控制已验证”。本轮只有文档修订，开发任务与协作验收仍须真实执行。MS-22 用实际记录检查选用模式；不会因模板或字段存在就宣布多 Agent 团队已跑通。

## 10. 文档怎样像代码一样管理

### 10.0 分析报告只作参考，不直接作为项目结论

**用户本轮明确要求：模块分析报告只作参考资料。** 无论标题或正文是否写“已验证”“权威基线”“深度还原”，报告都不能自行取得规格、事实或验收结论的效力。多份报告互相引用也不增加独立证据。

产品取舍回到用户明确决定；硬件与接口事实回到原始 SDK/源码、厂商资料、实际固件或可复核实测；设计选择由相应 Owner 按范围评审接受。报告只提供问题、候选方案和查证线索；引用了原始资料时仍须检查实体、版本和适用范围。找不到或未核对原件的关键内容标 `[UNVERIFIED]`。已批准的设计也不能把未验证的物理参数变成已证实事实。

### 10.1 文档放进 Git，Obsidian 是编辑器和阅读器

**需求、架构、接口契约、测试计划、任务规则和发布说明都应作为文件放进 Git。** 这样每次修改都有 diff、作者、时间、评审和回退记录。Markdown 可以继续用 Obsidian 打开，Obsidian 的双链和 Canvas 只是阅读体验，不代替 Git 的版本历史与审批记录。

当前规划资料保存在 Obsidian Vault 的 Git 仓库中，可继续作为 M0 产品定义阶段的权威文档位置。Linux 代码仓和协作控制仓落实后，做一次有记录的迁移：选定唯一正式仓、记录旧/新仓提交 SHA、列出迁移文件和旧文件状态。迁移完成后，Vault 只留导航或只读引用，不再和新仓各自修改同一份正式文档。

如果代码是一个仓库，可把文档放在该仓的 `docs/`。采用下面的混合布局时，跨模块需求、决策和计划放在唯一 `project-control` 仓；可执行 API/IDL/schema 和细化 ICD 默认放在 `soc-ap/contracts/`，与相关实现、消费者和测试一起审查。模块构建说明放在对应代码仓。每种对象各有唯一原件，不要求所有对象挤进一个仓；生成文件和文档引用标明源 commit/版本，不维护第二份定义。

### 10.1.1 推荐的项目目录和 Git 仓库划分

在 Linux 开发机建立一个**纯工作区目录**，里面并排检出多个独立 Git 仓库；不要把一个 Git 仓库嵌套进另一个仓库而不使用明确的 submodule/manifest 管理：

```text
printer_project/                 # 仅工作区目录，本身先不设 .git
  project-control/                # 一个独立 Git 仓：docs、需求、ADR、计划、任务、集成版本锁
  soc-ap/                         # 一个独立 Git 仓：contracts、应用、模拟器、测试；按目录分工
  mcu-p3/                         # 一个独立 Git 仓（已有仓）：包含运动主控 MC (AT32F435) 与工具头从控 TH (AT32F423CCT7)
  vendor-sdk/                     # 厂商 SDK 按其原有 repo/manifest 锁版本，不随意复制改写
```

**默认不把每个 AP 功能模块立刻拆成独立 Git 仓。** `soc-ap` 初期可以按 `forward/`、`job/`、`state/`、`gateway/`、`ui/`、`middleware/`、`sim/`、`tests/` 划分目录，每个目录有唯一 Owner 和写入白名单；Agent 用分支/worktree 隔离修改，再由 CI 做整体集成。模块边界稳定、需要独立发布、独立权限或独立负责人时，再考虑拆仓。

单独的 `project-control` 仓记录“为什么做、做哪些、依据哪版契约、结果如何”；`soc-ap` 保存可执行契约与代码，让 AP 内部接口变更和消费者修正可以在同一 PR 完成；双 MCU 固件统一在已有的 `mcu-p3` 仓中维护，由 ENG-MC / ENG-TH 负责掌管。目录树是建议，不表示仓库已完成环境交接。

如果未来某个功能确实独立成仓，它至少应满足：①单独负责人和清楚的代码边界；②稳定且有版本号的 API；③可单独构建和测试；④有独立发布理由；⑤跨仓集成测试能验证兼容。缺少这些条件时，拆目录即可，不拆仓。

`project-control/` 中增加一份受审查的集成清单，记录各仓 URL、已验证 commit、REQ/ICD 版本、契约包/哈希、SDK/镜像与 MC/SCM 固件版本/哈希，以及构建方式。演示/发布用清单锁定版本，不能使用“各仓最新主分支”拼装。若 SDK 使用多仓 manifest，则保存 manifest commit 和各子仓 SHA；未知或没有的固件要明确标注。

### 10.1.2 文档仓与代码仓怎样配合

推荐的数据流是：

```text
产品决定/问题单
  → project-control 的需求/ADR PR
  → 相关 Owner 审查并批准
  → 在看板建立带 REQ/ICD 版本的细任务
  → soc-ap 提交契约、实现、消费者和测试的配套 PR
  → 需修改生产 MCU 时，其负责人按准确契约版本提交对应固件 PR
  → 集成清单锁定各仓 commit
  → CI/QA 在锁定版本上验证
  → 测试报告与发布记录回链到 project-control
```

AP 公共接口与新 AP-MC 试验契约默认以 `soc-ap/contracts/` 为原件，带版本、Owner 和适用状态。ARCH 负责契约决定，指定作者按任务实现；同仓变更由一个集成负责人组织契约、必要消费者和测试在同一 PR 接受，不人为拆成不可运行的中间版本。管理仓的接口目录只链接原件和准确 commit。

既有 MC-SCM 协议以原固件/原始协议资料为依据；未交接完整前只登记来源、缺口和模型假设，不把重写的说明当成真实原件。跨仓 MCU 消费者使用锁定版本的契约包/tag/hash，固件负责人须接受生产协议；集成清单锁定经测试的组合。临时不同步的组合不能作为通过版本。独立契约仓以后只有在确需跨产品独立发布且具备兼容检查时再考虑。

### 10.1.3 三种拆分方式怎么选

| 方式 | 优点 | 代价/风险 | 适用时机 |
| --- | --- | --- | --- |
| 所有代码、文档一个 Git 仓（单体仓） | 初期最省管理；同一提交可原子改契约和多个模块 | SoC/MC 工具链、权限和发布节奏不同；大型 SDK 仓可能重 | 团队很小、仓库结构简单、暂时需要快速原型 |
| 管理文档一个仓，契约随 SoC 模块化仓，MC 固件分仓 | AP 契约、代码和消费者可同一 PR 集成；符合固件维护边界 | 文档引用要锁版本，AP/MCU 仍需跨仓兼容验证 | **当前推荐默认**：架构仍在收敛，MCU 人员待落实 |
| 文档仓＋每个功能模块独立仓 | 每个模块权限、发布和团队完全独立 | 一个端到端功能需多个仓同步升级；容易版本漂移、接口悬空、CI 复杂、AI 跨仓上下文增加 | 模块 API 稳定、团队和发布高度独立后再采用 |

因此，你提出的“一个项目目录＋独立 docs Git 仓＋多个代码 Git 仓”**可行**；我建议把“每个功能模块都单独 repo”改为“确实独立的产品/固件边界才单独 repo，SoC 应用先一个模块化 repo”。仓库怎么分属于可调整的实现管理选择；文档、接口、任务和版本必须只有一份权威来源则是硬规则。

### 10.2 按文档用途分目录，不造很多重复副本

建议的权威文档结构：

```text
docs/
  README.md                 文档入口、权威来源和当前批准基线
  product/                  产品目标、功能目录、需求 REQ 和验收条件
  architecture/             系统边界、ADR、模块责任和状态所有者
  interfaces/               接口目录、Owner、来源链接及锁定版本；不重复可执行定义
  plans/                    版本范围、里程碑、依赖和交付计划
  testing/                  测试策略、场景、独立预期结果和验收报告
  operations/               构建、模拟器、开发板、恢复和发布手册
  decisions/                需要产品负责人或硬件 Owner 决定的事项
  archive/                  已被替代但需保留追溯的旧方案
```

这只是可读的目录，不需要为了形式一次创建所有空文件夹。主文档通过 Obsidian wikilink（在 Vault 内）或相对 Markdown 链接（跨仓/代码仓）指向唯一原件。相同内容不复制成“给 AI 版”“给经理版”“最新版本”三份；需要不同读者版本时，由权威文件生成摘要或导出。

### 10.3 每份正式文档都标身份和状态

正式文档头部至少记录：`doc_id`、`status`、`owner`、适用产品/版本、所依赖的 REQ/ADR/ICD ID。当前方案的文档修订批准记录见 [[AI_SoC_协作方案/collaboration_revision_20261008_083854]]，不把修订批准扩成全部产品或契约批准。Git commit 已经记录实际时间和改动人；若 YAML 中保留更新时间，必须按仓库规则用真实时间生成，不手工猜秒数。

以下是正式输入的 `approval_status`；已有 `status: current-plan/current-guide/...` 继续表示文件用途，不等于批准。接受记录另列接受者、准确版本、适用范围和依据。

批准生命周期使用：

- `Draft`：讨论稿，不能作为实现依据。
- `InReview`：等待指定角色评审。
- `Approved`：已有明确批准记录，可用于指定版本开发。
- `Superseded`：由新文档/版本替代，保留链接和替代关系。
- `Rejected`：保留决定原因，不能被误认为仍有效方案。

文档生命周期和适用范围分别标注：`approval_status: Approved` 表示有对应接受记录，`usage: Experimental/Production` 表示适用范围。模拟试验依赖已接受的试验契约；调查/设计可以把 Draft 作为待核查材料。旧文件中的 `experimental` 也只表示试验范围，不能升级成生产规格。

### 10.4 不同文档由不同角色负责批准

| 文档 | 主要撰写者 | 必须评审/批准者 | 变更影响 |
| --- | --- | --- | --- |
| 产品范围、功能目录、REQ、验收 | PM | 你/真实产品负责人 | 影响版本范围和任务拆分 |
| ADR、系统图、模块/状态责任 | ARCH | 受影响 Owner；产品范围变化再请产品负责人 | 影响模块边界、依赖与资源 |
| AP-MC、MC-SCM、业务 API/消息 schema | ARCH 与接口 Owner | 两端实际实现者、QA；生产 MCU 契约须 MCU Owner 接受 | 影响所有生产者、消费者、模拟器和测试 |
| 模块 README、构建说明 | 对应工程师 | 模块 Owner/Reviewer | 影响该模块开发与维护 |
| 测试计划和预期结果 | QA | 产品/需求 Owner、相关工程师 | 定义通过/失败证据，作者不能单独批准自己的预期 |
| 测试报告、发布记录、已知问题 | QA/INTEGRATOR | 按类型由独立 Reviewer 核对；发布记录另含 QA、INTEGRATOR 与发布负责人 | 绑定具体版本；作者不得靠换岗位名自批，普通 QA 报告不机械要求再次运行 QA |
| 看板和任务状态 | COORD | COORD 按证据更新 | 反映进度，不改变产品需求或接口 |

### 10.5 文档修改按一次小变更走 PR

1. 先建一个 `DOC` 或 `RFC` 项，写清楚为什么改、哪些文档和功能 ID 受影响。
2. 在分支上修改权威原件；不要直接改已批准文档的历史含义，不要同时编辑多份副本。
3. Diff 只包含一个主题：比如改变一项功能范围，或改变一个接口字段；大重构拆成多个小 PR。
4. PR 写出旧行为、新行为、依据、尚未解决的假设和受影响的任务/测试。
5. 按上表找正确 Owner 评审。改变用户可见范围须产品负责人批准；改变共享 API 须生产者和消费者评审；改变安全边界须相关真人工程师审查。
6. 未部署自动化前人工检查 Markdown、链接、frontmatter 和 schema；部署后由工具检查格式，人工仍检查事实来源、兼容性和验收。
7. 合并后更新 README 索引、相关任务和功能追踪表；只有正式批准后才派实现任务。

紧急纠错可以先撤回有问题的任务或制品，再补 RFC/PR 留痕；不能以紧急为由让正式需求长期只存在聊天记录里。

### 10.6 每项功能和接口都能追到实现与测试

使用稳定 ID，而不是靠标题猜测：

```text
FEAT-FILE-003 → REQ-014 → ADR-008 / ICD-JOB-v2
              → TASK-024 → commit 3f... → QA-REPORT-011 → release candidate
```

一项功能的修改若影响公共契约，PR 必须列出 API/ICD 的全部生产者、消费者、模拟器和测试；相关任务一并标记需更新。契约版本提高后，旧版本测试不能冒充新版本通过。废弃 API 先经过迁移期和删除验收，不由某个 Agent 静默删字段。

### 10.7 AI Agent 读文档和交文档的规则

- 派单只提供“本任务所需文档列表＋精确 Git commit/版本＋任务卡”，不要把整库灌入每次上下文。
- 授权先遵从当前项目规则和用户有效指令；设计执行依据已接受的 REQ/ADR/ICD 与任务卡。模块分析报告、研究笔记和旧讨论均为参考，不能覆盖正式输入，也不能仅凭“已验证”的措辞成为正式输入。硬件/协议事实另按原始来源核对，发现与规格冲突时记录并重新评审受影响部分。
- 研究发现先写 `Open Question` 或 RFC，不直接覆盖批准基线。
- Agent 修改共享接口只提交提案；由 ARCH 和实际两端 Owner 审批后更新权威契约。
- 每次交接附：改了哪些文档/代码、依据链接、基线和契约版本、已做/未做、测试证据、假设和阻塞。
- 对话用于通知、澄清和决策；一旦影响需求或接口，COORD 登记明确决定及批准依据，通知对应文档 Owner 更新权威原件并绑定版本。COORD 只有获得该文档具体写入授权或明确兼任时才修改，不因协调身份取得所有文档写权。

### 10.8 从最简单的工具开始

初期只需要 Git、Markdown、代码审查（PR/MR）和一个由 COORD 维护的任务看板。先人工检查 frontmatter、链接、文档状态和需求追踪；等重复劳动明显时，再加链接校验、schema 校验和看板生成 CI。不要先建复杂文档平台或 Agent 服务，之后才讨论产品本身。

## 目录限定、能力条件与组合证据

功能引用使用 `PM:FEAT-…` / `SOC:FEAT-…`。SOC 维护原件为 product_feature_catalog_baseline，日期版仅历史快照；PM→SOC 一对多映射与子需求一起追到 REQ/ADR/ICD、微步/细卡、候选版本和独立证据。产品 Open、源码启用、接口可用与验收通过分别记录。

`dependency_conditions` 是可用性门禁，不代替 `depends_on`：例如 MS-04 需 TASK-005 内 MCQ-06 或等效现成接口证据；调查 Done 的否定结果不能使下游 Ready。结构化 MCQ 微步按原卡记录，实际开工前映射文件、命令、检查者/收件与租约，不直接派 TASK 整包。

组合环境：document/source-reviewed、host-build、Ubuntu Mock 工具、ubuntu-host+real-mcu-hil、未来目标 SoC 分开；证据层级不是完成范围。运行前锁定 MC/TH 源码/工作区差异/配置/制品哈希、契约、场景、端点、时间、TX/RX/轨迹；原报告不自动证明最新组合通过。

保留当前微步/QA 历史。后续按可验收能力拆票，同一作者、仓库和契约下的声明/实现/构建/自检放在一张有界卡的内部检查点；函数规模门禁不要求一函数一任务。每个执行者只持一张活跃实现卡，完成准确候选后安排独立检查。同一冻结候选可批次审阅，但逐票/逐必需角色绑定版本和结论；QA 作者产物的非作者复核及硬件门禁按原规则落实。失败按原文→根因→修正汇报，只回退本票差异并保留用户修改。执行成本、联调和派单粒度以[当前重排](../../docs/planning/workflow_replan_20261028.md)为准。

Windows COM8 与 Ubuntu USB 直通的同一 CH340 不可同时占用；MC/TH ST-Link、串口和板卡分别记录资源/期限，TH COM6 仅诊断。QA 提交签署证据或事件，由唯一 COORD 投影正式状态；未登记实际 COORD/独立 QA 不得虚构已执行或已放行。
