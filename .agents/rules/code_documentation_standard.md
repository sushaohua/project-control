# 代码注释与文档字符串规范

## 1. 适用范围与语言

- 本规范适用于本工作区各仓库的自研 C/C++、Python、Shell、HTML/CSS/JavaScript 等代码，包含 `project-control/` 下的 Runner、检查器、构建部署脚本及 QA 工具和测试代码。
- **全部新增或修改的说明性代码注释、模块/类/函数文档字符串（docstring）必须使用中文。** 标识符、API 名称、协议字段、命令、路径、单位及必要技术术语保留原文；中文要求不改变程序标识符、日志或对外接口。
- shebang、编码声明、许可证/版权声明、工具识别指令和必须逐字保留的上游引用保留规定格式；新增解释使用中文。
- 新增自研代码执行本规范；修改存量自研代码时补齐本次变更涉及的接口与关键逻辑说明。第三方、自动生成代码及无关历史代码保持最小修改，不因本规范批量翻译或扩大重构。

## 2. 必须说明的内容

- **模块职责**：新增模块在文件头说明用途、主要流程或数据流，以及关键边界。Python 使用模块 docstring，其他语言使用对应注释形式。
- **公共接口**：公共函数、类和方法说明用途及适用的参数约束、单位/取值范围、返回值、错误或异常、资源所有权、调用前提与副作用。C/C++ 在公开声明旁说明；Python 使用中文 docstring，类说明职责，公开方法说明具体行为；Shell 说明调用参数、退出码和外部影响。只写实际适用的内容，不堆空模板，不在声明与实现重复抄写。
- **关键逻辑**：状态转换、协议映射、超时与重试、并发与锁、硬件时序、安全保护及兼容处理，在对应实现附近说明设计原因、成立条件和失败处理；内部辅助函数有隐藏约束时也必须说明。
- **配置与常量**：对不能从名称直接判断的配置项和常量，说明含义、单位、默认行为、有效范围，以及适用的零值/禁用和超时语义；优先放在定义处，其他位置引用。
- **测试与故障工具**：对不直观的测试预期、故障注入和夹具限制，说明预期依据、验证范围及必要的现场恢复条件。

## 3. Python Runner 的重点要求

Runner、调度器及检查器除遵守上述通用要求外，还须在相应实现处解释实际存在的以下机制：

- 状态转换的前置条件、完成条件及异常分流。
- 租约的获取、续期、过期、释放及进程存活与资源占用之间的关系。
- CAS 的比较对象、冲突处理，以及重试、幂等和崩溃恢复的边界。
- 子进程的启动、超时、退出判定、清理和遗留进程处理。
- 候选版本、报告、原始证据的绑定对象，以及校验失败时的处理。
- 可能抛出的异常、文件/数据库/网络写入等副作用和资源释放责任。

按模块实际包含的机制说明，不要求每个函数重复列出整张清单；注释必须描述当前实现，不能把计划能力写成已实现行为。

## 4. 维护与检查

- 修改代码行为时同步更新相关注释，删除或修正过时说明；注释不得与实现、接口契约或测试预期矛盾。
- 注释优先解释目的、原因和约束；名称及直白语句已经表达清楚的简单内部代码无需逐行复述。不规定注释比例，不要求每个简单辅助函数写长篇说明。
- 代码作者交付前检查本次差异的中文注释、接口说明和关键逻辑说明；独立 QA 在既有代码审查中核对，不增加单独审查轮次或报告字段。
- 缺少上述必需说明时，审查意见应指出具体位置及缺失的约束；纯措辞或排版偏好作为非阻断建议，不以“注释不够多”作为拒绝理由。
