# 正常流程E2E与Issue验证流转规则

本规则补充[交付验收门禁§4.1～4.3](delivery_and_coord_gate.md#41-正常流程优先与正负成对验收2026-11-02)。沿用现有任务状态、角色分工、服务器候选、独立QA、返工上限和硬件授权；任务卡仍是执行状态原件，不增加第二套调度系统。

## 1. 生效范围及记录保护

- 适用于新建、未完成任务及后续复验。纯文档/调查任务按其范围核对来源与结论，不机械要求真实硬件；实现、集成和系统验收按预先接受的证据范围执行。
- 已有Done和原始报告保留原候选、范围及签署。新一轮检查新建run；旧结论不足时追加限制或撤回依据，由COORD据证据调整适用关系，不回填历史实测、不批量改旧卡。
- 正常流程E2E只验证本轮锁定候选。冻结功能保持冻结；当前选项A加热0%等有效安全约束继续执行，测试计划不扩大烧录、加热或设备操作权限。
- 任务模板与报告模板中的新增条目按本规则适用范围补充，旧文件不批量迁移。尚未适配的机器schema/检查器由COORD登记工具缺口，以人工核对记录补充，不把规则发布当作检查工具已部署。

## 2. 角色、输入与测试顺序

1. COORD先核查在途任务、候选、用户改动和资源占用，查重后选择现有验收卡或创建关联卡。落实实际会话、写入范围、独占时段和既有返工预算，不重复派单。
2. QA编制正式测试计划与编号清单，列全当前用户入口/API及可测、未实现、冻结项；ARCH与相关Owner核对独立预期、触发归属、超时和证据。QA作者产物按现行规则由非作者独立复核。
3. INTEGRATOR交付锁定的各仓服务器commit、配置/依赖/制品哈希、设备与固件身份、构建部署说明和自身集成记录。独立QA从同一候选自行准备隔离环境并重新构建部署，在COORD分配的台架窗口执行真实HIL，分别保留自己的运行和环境证据。
4. 先确认正常台架前提，再从用户入口逐功能运行正常testcase。基线故障按证据区分设备/环境问题与软件问题，不把“硬件假定正常”当作实测事实，也不将上位机未触发探测归咎于硬件。超过契约期限仍UNKNOWN或无响应时登记失败；根因待调查。
5. 某用例失败时保留版本和现场，建立Issue及关联证据；依赖它的用例记阻塞，独立用例继续。完成正常流程核查、必要修复及回归，再执行完整故障注入、恢复和稳定性测试。安全前检不受顺序限制。
6. 收件按交付门禁逐项核对必测清单和证据，不能以负例通过、测试名称存在或已有APPROVED替代本轮正常路径执行。

## 3. 触发源、正负配对与用户旅程

每项适用功能至少记录：功能/需求ID、用户入口、正常前提、触发者与事件、动作及期限、预期状态/硬件效果、正负配对用例、恢复用例、证据层级。接口契约要区分已接收与已执行完成，并说明数据新鲜度、缓存失效和重连行为。

依赖MCU的向导或状态显示至少覆盖以下配对，具体期限、协议和成功条件由ICD确定：

| 正常路径 | 对应故障/恢复路径 |
| --- | --- |
| 硬件已连接时冷启动，自动探测并显示真实版本与有效数据 | 不连接、超时或坏响应时明确未就绪/失败，不伪造全绿 |
| 软件先启动再连接硬件，实际触发探测并更新状态 | 单独MC或TH失联时分别显示状态；旧缓存不作为新响应 |
| 完成向导后进入约定工作台，适用完成标志持久化 | 请求失败/重复点击/刷新重启时保持状态一致，提供明确重试或下一步 |

健康硬件条件与传感器结果满足预期后才能判在线/就绪；收到任意帧不等于所有功能健康。Mock正例只能证明软件范围；真实HIL正例须取得真实硬件应答和适用物理效果。

## 4. Issue登记与派单

Issue是缺陷及验证索引，沿用关联任务的`Backlog → Ready → InProgress → Review → Verify → Done`，不新增任务status或`task_kind: bug`。Issue验证记录由实际发现者填写，COORD负责查重、关联任务、优先级、派单与最终关闭。

- 在途任务范围内发现的缺陷，优先回原卡退修并按现行规则修订revision，保留原报告；不另开子票隐藏拒绝或重置返工计数。
- 已Done后新发现的缺陷，保留旧版完成记录，建立关联的修复/复验卡。根因未知用`investigation`，已明确实现范围用`implementation`；跨模块按现有Owner边界安排关联任务。
- 同一根因合并关联多个用例；不同根因独立记录。初步现象不写成已确认根因，例如“向导超时仍UNKNOWN”与“后台未发送GET_VERSION”须区分观察和待验证推断。
- 台架缺失、访问失败或隔离证据不足登记环境阻塞与解除条件；按交付门禁§5.3处理，不反复派作者修改无关业务代码。影响安全或其他用例前提时暂停受影响动作，独立工作可继续。

默认在`project-control/docs/issues/<COORD分配的Issue-ID>.md`保存，已有可追溯问题记录可直接引用，不重复复制。以下仅为字段约定，空值不是有效派单或通过证据：

```yaml
issue_id: null
summary: null
resolution: open # open / fixed / duplicate / not-a-defect；不是任务status
reported_by: null # 实际会话或操作者
source_task: null # task_id/revision/run
feature_and_case_ids: []
affected_versions: {} # 各仓commit、配置、制品及实际设备/固件身份
preconditions: []
reproduction_steps: []
expected: null # 正式需求/ICD/预期版本、成功条件及期限
observed: null
evidence: [] # 实际路径/哈希、日志/帧/截图/录像；缺失明确登记
impact: null
priority: null # COORD按影响与依赖确定，安全/主流程阻断优先
root_cause: null # 未查明保持未知；推断单列并注明待验证
linked_tasks: [] # 真实任务ID、revision、Owner；任务状态以卡为准
blocker_and_recovery: null
fix_candidates: []
verification_runs: [] # 独立验证会话、候选、原case结果、相关回归及证据
duplicate_of_or_disposition: null # 重复或非缺陷须有对照依据
closure: null # COORD、依据及记录；未验收不关闭
```

## 5. 修复、独立复验与关闭

1. Owner按白名单修复并提交`Issue → 根因 → 有界差异 → 测试 → 新服务器候选`映射，保留开工前用户改动。相关公共契约变更先经ARCH及生产者/消费者接受，不以修bug扩大产品范围或做无关重构。
2. 独立QA对新候选重跑原失败用例、对应正常/故障/恢复用例及受影响回归；真实HIL缺陷须回到真实HIL复验。不能只证明不再出现错误提示，也不能用作者自测关闭Issue。
3. QA对每例记录通过、失败、阻塞、未执行或不适用及依据，绑定准确候选、真实环境和原始证据。批准范围依交付门禁分别判定软件/HIL；缺环境或证据时保持未通过。报告schema未支持阻塞结论时保留待审并记录原因，禁止为填字段伪签APPROVED。
4. QA报告经非作者复核、必需Owner接受后，由COORD核对候选、原case与必要回归，才能将`resolution`置为`fixed`并登记关闭依据；关联任务完成仍按原状态门禁执行。重复或非缺陷的处理也须留依据，不能计作修复通过。
5. 同因复发、累计返工上限和升级沿用交付门禁§5.1，不通过换Issue、任务或run清零。后续复发追加新记录并恢复关联处理，保留此前关闭与适用范围。

## 6. 最小交付与收件

本轮方案和报告须提供：锁定候选；完整必测清单及逐例结果；正负配对与触发源契约引用；软件/HIL分别执行情况；真实会话/环境/设备证据；Issue与修复回归索引；明确的批准范围、未执行项及限制。测试工具和黄金预期版本同样锁定，录屏/截图不能替代真实通信和物理效果证明。

规则或模板的文档审阅通过只对文档有效，不表示服务器运行器、浏览器自动化、Issue系统或HIL已部署。COORD按本规则人工收件，并安排独立审阅新增流程文件；本规则没有代替任何实际QA签署。
