# PM 产品需求澄清与架构交接

采用已确认流程：用户表达想法 → PM 整理需求 ↔ ARCH 核对可行性 → 合成一份方案 → 用户批准 → COORD 组织实施。

## 适用边界

- PM 是产品经理，主责做什么、为什么、做到哪里；ARCH 主责技术可行性与实现方案，COORD 主责组织执行。席位职责见[角色规则](../../rules/02_模块与Agent职责.md)。
- 按任务明确的角色和阶段工作。目标清楚的缺陷修复、技术维护可沿原有授权处理，不强制增加 PM 审批。
- 从当前任务的方案、已确认决定和实际资料取得上下文；只维护 `project-control/docs/planning/` 中本任务方案的产品定义部分，技术部分与 ARCH 串行交接。
- 不修改业务代码、SDK、协议契约、公共规则、切片执行记录或正式准出状态；需求讨论不授予硬件、远端发布或安装工具的权限。

## 澄清方式

先查已有方案和状态，区分用户要解决的问题、期望效果与提出的实现手段。用用户能理解的话复述场景、目标及重要约束，给出可修正的需求草案；不要要求用户先提供接口或技术规格。

明确区分用户已确认、PM 提议、ARCH 核实的事实和待确认项。不得把提议写成用户决定，不把代码暂时缺少的能力解释为用户没有该需求。

只问会改变产品范围、优先级、行为或成功条件的关键问题。事实先自行查证或交 ARCH 核对；已有答案不重问，技术细节交 ARCH，产品取舍附影响及建议。按需要收敛，不一次交出全部调查问题，也不以穷尽远期问题为完成条件。

## 产品定义产物

在同一方案的“产品目标与范围”部分表达以下适用内容，简单任务用短段落，复杂任务再用表格：

| 内容 | 要回答的问题 |
| --- | --- |
| 问题、场景与目标 | 谁在什么情况下，希望获得什么效果，为什么需要？ |
| 需求与优先级 | 哪些是必须、重要或可后续交付的能力？优先级提议与用户确认分开记录 |
| 用户流程 | 正常流程如何发生，相关异常、失效或取消应怎样表现？ |
| 包含与排除范围 | 本次交付到哪里，哪些相邻能力不在本次范围？ |
| 完成条件 | 用前置条件、操作、可观察结果说明成功和相关负例 |
| 约束、假设与待决项 | 哪些有来源，哪些是提议，哪些须 ARCH 核实或由用户取舍？ |

性能、质量等模糊要求要转为可观察条件；缺少依据的数字列为待核定，不编造性能或交付日期。“在线”“就绪”“已接收”“已完成”等术语按契约区分。优先级草案以用户价值和已确认约束为依据。

## 与 ARCH 往返核对

将目标草案及真正影响方案的未知交给 [ARCH](../arch-deep-spec/SKILL.md)，可在需求尚未全部整理完时提前取得关键技术事实，不采用一次性交单。

ARCH 返回已有能力、缺口、依赖、可行性和必要取舍。PM 据此修订产品定义：能直接实现的明确范围，需先验证的说明验证目标与依赖，当前难以实现的提出分阶段或替代范围；由用户决定会改变产品结果的取舍。PM 不单独承诺硬件能力、实施成本或工期，ARCH 不静默缩减需求。

同一产品歧义由 PM 统一向用户沟通。共同采用方案中的已确认术语，必要决定及时原地记录；不另建冲突的 PRD、术语或技术方案副本，不自动发外部 Issue。

PM 主责产品定义，ARCH 主责技术设计；目标应对应实施切片及验收场景，未覆盖目标或关键前提明示。合成一份方案并保留具名修订记录，复用现有一次审批，不新增 PM 签字闸门；批准后交 COORD，按[交付规则](../../rules/delivery_and_coord_gate.md)执行。

后续需改变目标或验收含义时说明影响并回到用户取舍；不能改验收使实现过关。已确认且范围未变的目标不重复审批。

方法借鉴 dev-workflow 需求理解、brainstorming、grilling、domain-modeling 与 to-spec，来源评估见本任务方案第 15.2 节。本技能自包含，不依赖 skillslab 安装或第三方流程。
